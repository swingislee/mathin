# 加载缓慢的根因定位与第一批根治

- 目标：复盘近两个月线索／沟通／测评／学生页的读取优化为何仍慢，并处理老师“班级列表 → 课次 → 进入教室”链路；面向慢网与旧设备。
- 环境：本机隔离开发库（WhiteHouse，`127.0.0.1:35421`）与 3130 开发服务；另以本机生产构建（`next build` 独立目录）做同库 A/B。生产仅做只读核对，未部署、未迁移。

## 根因

1. **每次请求现算全部派生状态。** 名单 RPC 先为全校学生与线索推导阶段（`student_record_index_for_population`），再为整个阶段人群编排来源分组和上下文，最后逐行拼详情。成本取决于全校数据量而非本页行数：主管“我的名单”为 0 行也要 190–310ms。预存阶段索引的回滚实验只省 150–250ms；剩余约 400ms 名单编排与 20 行约 370ms 详情仍在每次请求重算。过去两个月约 60 个性能提交在逐段改写这条链，每段变快，结构不变，因此始终停在秒级。
2. **每个请求的固定鉴权开销。** proxy、布局、页头、页面守卫与读取函数各自调用 `auth.getUser()`，每次往返 GoTrue（本机约 60ms），一次页面 4–6 次；链接预取同样支付。
3. **SQL 内 N+1。** 待报名、续报、停课行逐行完整读取，逐行推算的年级随后又被批量推算覆盖；100 行约多 4 秒。
4. **首屏 JS 与字体。** 后台页首屏 JS 550–890KB（gzip）；班级详情、课次页因作业按钮与课件预览判断引入 three.js、全部教具合同与课件 zod 校验。冷加载另有约 575KB 文楷字体分片（`font-display: swap`，不阻塞文字）。
5. **网络与主机。** `mathin.club`、`supabase.mathin.club` 经 SakuraFrp 节点中转；生产为 i5-8250U 笔记本。往返次数与传输量在这条链路上放大。
6. **测量口径。** 既往数据多为快机器上的数据库或 HTTP 计时，没有慢网、降速 CPU 的浏览器端测量，也没有体积与往返预算。

## 待决定与后续

- 当前年级：`students`／`leads` 已有 `grade_basis_code`／`grade_basis_year`，但开发库 0 条有值，读取时每次回溯导入记录推定基准。建议导入与创建时写入基准、存量一次回填，读取只做学年加法；回填会改变“新导入覆盖旧推定”的优先级，需确认规则。
- 登录设备管理：会话表含设备标识、IP 与最近刷新时间，可做“登录设备”列表与逐台注销；是否需要、是否做教室设备模式待确认。

- **线索／沟通／测评／学生的读模型（根治项，需确认后实施）：** 按学生／线索保存阶段、名单编排字段与行详情，写入时按主体失效并在事务提交时重算，广域变化和跨日转为后台重建且期间回退现算；读取只按员工可见范围过滤、聚合与分页，补算 canWrite、协作归属等与员工相关的字段。可见性已核对：有沟通查看权限的员工，学生可见即其线索可见，阶段与详情可与全量视角共用。需与 Codex 当日并行修改的同组函数协调，并需生产迁移授权。
- 上课页仍为 802KB：`tool-classroom.ts` 汇总全部教具快照 schema，需按教具类型懒加载（课堂同步改造）。
