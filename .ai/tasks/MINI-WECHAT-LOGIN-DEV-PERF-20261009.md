# 小程序微信登录开发入口耗时

- 用户反馈：本地微信登录的 52 秒等待过长，需要解释并改善。
- 已确认：锁定 Next 的 `log-requests.js` 将 `next.js` 标记为框架准备时间，不等同纯编译时间；上一轮“编译 52 秒”的表述已向用户更正。业务处理约 350 毫秒。
- 环境：现有共享开发服务使用临时 Webpack 模式；历史小程序记录说明此模式用于绕开当时 Turbopack 的 PostCSS 模块缺失。此次检查时 32 GiB 内存只剩约 2 GiB 可用，开发 worker 私有内存约 2.35 GiB；这些是实测环境因素，尚不能据此分摊 52 秒耗时。
- 改进：为参与人微信登录/状态与开户建立独立路由，直接复用现有鉴权处理，脱离包含课表、测评、活动、服务联系与媒体等模块的通用入口。
- 本地依赖修复：`@tailwindcss/postcss` 的 `@alloc/quick-lru` 链接指向缺失目录。按 `pnpm-lock.yaml` 的 5.2.0 版本及 SHA-512 校验值，从 npm 官方源恢复本地包；没有变更依赖版本或锁文件。PostCSS 直接加载通过，3130 已恢复默认 `node scripts/dev.mjs`（Turbopack）。
- 耗时：拆分路由后，旧 Webpack 进程的首次请求仍有 33.1 秒框架准备，说明拆分本身不足以解释或解决全部等待。依赖修复并重启到默认编译器后，微信状态入口首次请求 HTTP 200，客户端 535 毫秒（服务端 511 毫秒，其中框架准备 483 毫秒）；随后真实微信 code 登录 HTTP 200，客户端 306 毫秒，返回 `onboarding_required` 并签发开户票据。不同进程状态的单次观测不构成稳定性能保证。
- 检查：两个新增入口的定向 ESLint 通过；微信登录及开户无效请求均返回 400；真实微信登录通过；局域网登录页面与生成的 CSS 均返回 200，热加载页面约 151 毫秒。现有认证业务处理未修改，复用此前的定向认证检查，不重复全库验证。
- 剩余：网页登录页和推广页的首次准备仍分别约 36.1 秒、47 秒；整站冷启动尚未解决，不能用微信入口的改进替代该结论。如继续优化，应从大页面依赖与开发编译分析开始，不重复已经通过的登录验证。
- 状态：本次安全增量已完成，开发端可操作，待产品负责人继续微信手机号授权和开户验收；没有更改数据库或生产服务。
