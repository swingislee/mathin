# 学服工作台与跨场景快捷登记：升级方向

> 适用项目：`swingislee/mathin`  
> 编写日期：2026-09-06  
> 代码参考基线：`main @ cddc7c7b4be46d2a66bc3fb70005e4192f984b3c`  
> 文档用途：指导执行 Agent 在现有系统上升级本轮开发中的学服功能。本文中的目标行为属于本轮方案；代码基线用于定位复用点，不代表生产环境已经实现。  
> 实现前提：按目标方案直接重构，本轮涉及的旧沟通入口、旧工作单、旧接口和旧开发数据结构不承担向后兼容要求。

## 1. 本轮要交付什么

保留现有按工作环节组织的表格，把跨阶段的跟进记录、邀约和报名等快捷登记能力接到各个工作现场。

**主要交互统一为：表格主行展示关键信息和操作 → 点击操作 → 在当前行下方展开对应登记面板 → 保存后继续处理当前名单。**

学生入口提供按人查找和随时记录的能力。它与各工作台使用相同的登记模块；学生名单以后可以增加紧凑卡片视图。

用三个例子理解目标：

- 学服正在批量登记测评：在测评行下同时填分数、教师建议、家长反馈；家长约好公开课时，再展开活动模块，一次提交，继续下一位。
- 家长突然发来微信：从学生名单找到孩子，写一句当下情况就能保存；聊出测评邀约或报名结果时，再展开对应模块。
- 学生缴费确认学位，但还没有合适班级：在分班中保留为等班；等待期间从当前行继续记录家长反馈。

**统一的是业务记录与登记模块，表格仍然是学服工作台的主要工作形式。**

## 2. 页面入口与名称

本稿建议将原“跟进”入口命名为 **学服工作台**。执行时采用这个名称；页面、路由和模块按新的职责组织，所有站内菜单、链接及调用同步更新。

```text
学生
学服工作台
  ├─ 线索
  ├─ 首联
  ├─ 测评
  ├─ 分班
  └─ 续班
活动
```

| 入口 | 学服的工作场景 | 主要表现形式 |
| --- | --- | --- |
| 学生 | 现在要找这个孩子、看整体情况、随时记事 | 现有名单接入快捷登记；紧凑卡片是后续可增加的展示方式 |
| 学服工作台 | 现在要集中处理一批线索、首联、测评、分班或续班 | 表格、行内关键操作、行下详情面板 |
| 活动 | 现在要处理某场公开课或其他活动 | 保留活动组织方式，参与名单使用行内操作与行下登记 |

### 五个工作分区的职责

| 分区 | 本页主要登记内容 | 关键说明 |
| --- | --- | --- |
| 线索 | 来源、原始信息、查重、负责人分配 | 原始获客名单可以先关联线索身份；来源记录持续保留 |
| 首联 | 联系结果、线索有效性、必要资料与身份确认 | 首次有效了解是主要目标；未接通的多次尝试也保存在这里 |
| 测评 | 测评预约、到场、成绩、专业判断、教师建议 | 一个学习阶段通常有一次主要测评；需要复测时另留记录 |
| 分班 | 报名结果、缴费确认学位、有班入班、无班等班 | 测评建议用于匹配班型；正式学位与正式入班分别记录 |
| 续班 | 下一期课程选择、续报情况、学位和入班衔接 | 本期在读与下期续班可以同时进行 |

“首联”专指第一次有效了解及必要建档。之后的跟进通过各处共用的登记模块继续记录。分区顺序用于组织工作；现场直接报名、跳过活动、必要复测等路径，按实际业务条件办理。

公开课按活动场次组织。同一个孩子可以在测评前、测评后、在读期间或退课后多次参加活动；每次参与分别保留。

### 开发阶段直接重构

当前“沟通”页同时承载首联、邀约协调、活动后联系、工作单和历史记录。[S4] 本轮按新职责直接整理：

- 首联分区突出待首次有效了解和待补充必要信息的名单；后续沟通由学生入口和各业务现场的共用登记模块承载。
- 现有组件和业务能力按适用程度复用。旧沟通页面、工作单产品、接口及相关数据结构可以按需重构或移除。
- 路由调整后同步全部站内引用。旧 URL 重定向、旧接口适配、新旧双轨运行及旧工作单恢复均不作为交付要求。
- 旧开发数据的兼容、回填和迁移不作为本轮验收项。使用新体系创建的记录验证完整生命周期。

**这里取消的是旧版本兼容要求。新体系投入使用后，正常产生的首联、测评、跟进、报名和退课历史仍按本文规则持续保留。** 旧开发数据是否实际清理，按已确认的环境与数据安全规则执行；本轮重构范围不扩大到其他模块或正式数据。

## 3. 三条业务规则

### 3.1 身份持续关联，记录逐次积累

同一个学生可以出现在多个分区。每页展示与本页工作相关的事实，底层通过稳定身份关联。

身份未确认时使用现有 `leadId`；确认后关联 `studentId`，保留原来源和原记录。姓名和手机号用于识别、检索与核对，关联关系使用记录 ID。一个家长手机号可以对应多个孩子。

学生入口覆盖已经确认身份的各阶段学员，包括测后未报名、等班、在读和历史学员。原始未核实名单继续由线索和首联管理。直接导入的在读学员同样可以速记，其记录可以直接关联学生身份。

### 3.2 阶段标签推荐操作，业务事实决定结果

阶段标签主要从已有事实计算，例如：首联已完成、测评已预约、本阶段已测评、学位已确认、等班、在读。

学服保存真实业务记录后，标签和推荐操作随之更新。某个阶段需要的资料尚不明确时，可以显示“资料待确认”。

标签应带上必要范围：测评属于学习阶段；报名、在读、续班属于课程和期次。例如同一个学生可以“秋季数学在读、寒假数学待续班、数独课未报名”。

**最近一条记录出现在哪个页面，不能单独用来判断学生的阶段。** 学生在读后参加一次公开课，原有在读关系继续成立。

### 3.3 可以先记录情况，之后再形成安排

“家长担心孩子跟不上，具体原因还没问清楚”可以单独保存。

备注保存独立于去向、日期和下一步安排。默认使用当前记录人的身份与已有负责人关系，普通速记保持轻量。

| 情况 | 系统如何表现 |
| --- | --- |
| 只写下一个问题或一段反馈 | 保存跟进记录，更新最近记录摘要 |
| 学服主动标记值得留意 | 进入“需要留意”视图，之后可以解除标记 |
| 明确约定下次联系时间 | 保存约定，进入相应联系安排 |
| 已测评但目标课程未报名 | 出现在“测后未报”分类名单，供学服查看和选择 |

**测后未报、等班属于事实分类。单独保存备注不会自动产生联系任务、截止日期或“待安排”任务，也不被标记为工作遗漏。**

## 4. 表格与行下详情的统一交互

### 4.1 表格主行

主行保留本页原有核心列，在其中提供：

**学生标识 + 本页关键事实 + 简短当前情况 + 关键操作。**

跟进信息展示最近一条摘要和历史入口；长文本及详细表单放在行下。常用业务操作通常展示 2～3 个，其余收进“更多”。

“记情况”作为通用操作保持易找。阶段与当前现场决定优先展示哪些业务操作。

### 4.2 点击操作后，就地展开

点击“预约测评”“活动登记”“报名学位”等操作后，自动在当前数据行下方展开详情，并直接展开被选中的模块。

同一学生在这次登记中可以展开多个模块，例如活动登记和报名登记。切换模块时保留当前输入，主行位置与表格列宽保持稳定。普通记录点行可展开；主行内按钮、输入框与勾选框分别响应自己的操作，避免一次点击触发两种动作。

在测评页面点击“登记测评”时，成绩等业务字段直接展开；本次情况输入区同时可用。之后要登记家长反馈或活动邀约，都在这个面板内继续完成。

### 4.3 测评现场示例

```text
姓名       本次测评        当前情况           关键操作
张同学     三年级测评      已测评·秋季未报      [登记测评] [活动] [报名] [记情况]
┌────────────────── 当前行下详情 ──────────────────┐
│ 张同学 · 三年级测评                              │
│                                                 │
│ 测评：分数 82；建议 A+ 班；教师结论……             │
│ 本次情况：妈妈担心孩子跟不上，希望再看看实际课堂。 │
│                                                 │
│ 活动登记（点击主行“活动”后展开）                  │
│ 场次：本周公开课                                 │
│ 本次结果：确认参加                               │
│                                                 │
│                              [保存] [保存并下一位]│

李同学     三年级测评      待测评                ……
```

这一布局沿用仓库已有的 `FollowupInlineDetails` 结构。[S3] 本次重点是把相同登记模块接到这些面板里。

### 4.4 连续录入与草稿

- “保存”成功后更新当前行摘要与业务结果，保持正在处理的行和位置。
- “保存并下一位”仅在本次内容提交成功后执行，按当前可见名单顺序前进；下一位的模块、课程与草稿使用下一位自己的上下文。
- 保存后即使当前行已不符合原筛选条件，也先作为本轮已处理行留在当前位置；主动刷新名单、切换视图或分页时，再按最新条件整理。
- 打开其他行、切换操作和关闭面板时保护未提交输入；切回原行能恢复草稿，明确放弃时才清除。按本轮需要复用或调整草稿和名单稳定机制。

分班已有的班级行、花名册、学生名块、调班或座位操作可以保留。针对某个学生登记时，在所属行下展开详情，并清楚显示当前学生、课程和期次。

## 5. 共用的快捷登记体系

### 5.1 组成

各处共用以下四部分：

| 部分 | 内容 |
| --- | --- |
| 当前背景 | 学生、相关阶段事实、正在处理的测评／活动／课程／期次 |
| 本次情况 | 自由输入备注，能够独立保存 |
| 快捷登记入口 | 推荐操作与“更多”中的其他可用操作 |
| 业务模块 | 根据已选操作展开字段，复用现有业务表单和保存逻辑 |

在学服工作台和活动参与表中，它嵌入行下详情；在学生入口中，可以由名单行或紧凑卡片打开浮层。**同一模块在不同入口使用相同字段含义、验证规则与数据来源。**

### 5.2 模块如何推荐

推荐同时考虑 **学生当前情况、所在页面、正在处理的具体事项、当前用户权限**。

| 当前情况 | 优先推荐 |
| --- | --- |
| 首联待完成 | 联系结果、资料补充与身份确认 |
| 首联已完成，尚未测评 | 预约 1v1 测评、活动邀约 |
| 测评邀约已存在 | 更新原邀约、确认／改期；到场后登记测评 |
| 当前阶段已测评，目标课程未报名 | 活动邀约／参与、报名与学位 |
| 学位已确认、尚未入班 | 班级安排、可上课时间补充 |
| 正常在读 | 续班、活动、课程变动 |
| 某课程已经退课 | 记录情况、活动、重新报名 |

“记情况”在各阶段都可使用。其他符合业务规则和权限的操作可从“更多”进入；复测等合理例外由明确操作进入。

同一个孩子存在多个课程或期次时，优先使用当前表格行带入的对象。学生入口中单独写备注可以先不选课程；展开报名、续班、退课等模块时，再明确操作对象。

模块推荐采用简单、可测试的事实规则即可，本轮沿用固定模块配置。

### 5.3 各模块登记什么

| 模块 | 快捷登记重点 | 保存后的业务事实 |
| --- | --- | --- |
| 本次情况 | 沟通内容、家长反馈、现场问题、教师观察 | 一条跟进或观察记录；来源自动关联当前现场 |
| 首联与建档 | 联系结果、有效性、必要资料、确认或关联身份 | 联系记录及相应身份资料；未接通保留为待继续首联 |
| 测评邀约 | 愿意来待协调／已确认／改期／取消，按结果补时间与老师 | 新建或更新对应邀约；已确认预约进入测评名单 |
| 测评登记 | 本次测评状态、成绩、建议班型、专业结论 | 当前测评记录；后续可另建复测 |
| 活动登记 | 场次、邀约意向、确认参加、实际到场或未到场 | 对应场次的邀约、报名或参与记录 |
| 报名与学位 | 课程、期次、本次报名结果、缴费确认依据、是否有班 | 报名及学位事实；确认学位后分为已入班或等班 |
| 入班与变动 | 对应学位、目标班级、入班或调班结果 | 对应班级关系及变更历史 |
| 续班 | 来源课程、目标课程与期次、本次结果 | 对应续班轮次的结果及下一期报名衔接 |
| 退课 | 具体报名／课程、生效时间、原因、相关退款进度 | 对应课程关系结束，原学习与报名历史保留 |

表中的字段是业务语义，开发时映射到现有字段和接口；金额、收款、退款等事实继续使用既有财务能力。

### 5.4 点击模块，只表示要登记这方面的信息

邀约和参与需要保留不同完成程度。例如：

- 家长表达兴趣：保存反馈或意向。
- 家长愿意来但时间待定：保存待协调邀约，具体日期可以为空。
- 所需双方确认完成：保存已确认预约。
- 实际到场：登记实际参与结果。

现有测评老师、家长及时间确认规则继续适用。公开课“确认参加”与“实际到场”分别记录。

备注里的“准备报名”保存为意向。正式学位依用户明确操作和有效缴费确认依据建立。本轮业务采用 **先缴费确认学位，有班入班、无班等班**。

当前基线的报名确认函数允许从 `committed` 或 `payment_pending` 确认报名，因此代码中的“已确认报名”不能直接被改名为“已缴费”。[S6] 实现时核对并调整报名确认条件，对接有效缴费事实或受控的人工核验记录，按本轮规则确认学位。需要人工核验的情况显示“缴费待核实”，核验完成后再确认学位。纯备注不作为缴费凭据。

确认学位前可以保留推荐班型或候选班级；正式名额与正式花名册按已确认学位和实际入班关系计算。

## 6. 一次提交，各处一致展示

### 6.1 记录分别保存，关系一起关联

一次测评现场可能同时保存：测评成绩、家长反馈、公开课邀约。这三类内容分别进入现有业务记录，并关联同一个学生、各自业务对象及本次登记。

跨页面的效果应当是：

| 保存内容 | 原现场 | 其他入口 |
| --- | --- | --- |
| 测评成绩与反馈 | 测评行显示结果，原位可回看 | 学生详情展示测评和反馈；后续登记可以引用 |
| 公开课邀约 | 当前行显示新安排 | 对应活动名单显示报名／邀约状态 |
| 缴费确认学位、暂时等班 | 当前行显示报名结果 | 分班中出现等班记录，学生页显示等班 |
| 退课登记 | 当前现场显示该课程变更 | 学生页汇总变更，其他课程保持各自状态 |

跟进记录可以直接挂在学生或线索上，活动、测评、报名等上下文按实际关联。已在读且没有历史线索或活动的学生，也能正常速记。

首联后、测评后、在读和退课后的跟进使用统一的保存与读取约定，业务专属结果仍归入对应业务记录。检查现有通用跟进能力，适合本轮的部分直接复用，其余部分按目标模型重构；旧版分散的写入路径无需逐条兼容。每次事实保持一个权威来源。

### 6.2 重复、修订与统计

同一场次的确认、改期或到场优先更新对应邀约／参与关系，同时保留变更历史。参加另一场活动时新增另一条参与记录。

同一课程和期次的持续跟进关联原报名事项；新续班期次或退课后再次报名形成新的业务轮次，关联之前经历。重新报名时保留原退课记录。

一通电话产生两个业务结果，沟通次数仍为一次。单独录入分数属于测评登记；现场观察可以保存为观察记录。

“又联系了一次”追加记录；“刚才填错了”修订原记录。资料更正、业务变更、历史修订各自保留对应含义。新体系中的历史修订保持原作者、原发生时间和修订痕迹；已有修订机制可作为复用参考，接口与结构按本轮需要调整。[S7]

### 6.3 提交结果与安全

用户点击一次保存，提交本次填写的备注和业务结果。仅展开、未改动的模块不进入提交，也不触发必填校验；例如测评面板中的分数尚未填写，仍可单独保存家长反馈。

已填写但尚不完整的模块，提示补齐或明确选择“本次暂不提交该项”；暂不提交的内容保留为草稿。只填业务结果时，备注同样可以为空。

同域关联写入优先在同一事务中完成。确需分步调用现有接口时，要明确展示各项成功或失败，保留未成功部分的草稿；重试只处理未成功内容，避免重复记录或报名。全部必要内容保存成功后，才执行“下一位”。

每个提交需要防重复点击和安全重试。多人更新同一邀约、学位或班级时，提交前在服务端重新校验最新状态和容量，冲突时保留输入并提示。

前端操作范围和服务端权限保持一致。复用入口不扩大老师或学服的学生可见范围、财务权限与退课权限。学位登记不自动发起收款，退课登记不自动执行退款。

## 7. 学生入口与退课后的接续

### 7.1 学生入口

第一轮先在现有学生名单接入共用登记面板及跨阶段记录汇总。默认展示当前有权查看、由自己负责的学生，保留现有搜索、筛选与分页能力。

常用观察范围包括：全部负责学生、测后未报、等班、在读、历史学员、需要留意、已约联系。分类按实际课程和期次判断；多个条件可以并存。

学生详情优先展示最近背景，并能查看更完整的来源、沟通、测评、活动、报名和学习记录。完整历史按需加载，不因首屏条数限制而变成无法访问。

后续增加紧凑卡片时，每张卡只突出姓名与年级、简短当前情况、最近记录摘要。点击后用同一组模块登记。卡片排列属于展示增量，沿用相同业务逻辑。

### 7.2 退课

学生入口提供易找的退课登记；分班中的对应对象也可就地使用同一能力。

退课明确关联一门课程、一个期次、一次报名及相关班级关系。原缴费、上课、考勤、测评与沟通历史继续保留。结束一门课程时，其他课程的在读关系继续成立。

退款状态与课程关系分别记录并相互关联，沿用既有权限和财务流程。暂停、调班和退课使用各自的业务动作。

退课后的学生仍可在负责学生与历史学员范围中找到。登记时可以只留下原因，之后继续记录、邀约活动或重新报名；后续任务和联系日期按真实约定补充。

## 8. 工作名单与历史的呈现

五个分区都保留本页发生过的记录，同时提供适合日常处理的默认名单。

例如：获客批次保留来源；首联表保留当时联系结果；测评表保留本次分数；分班保留学位与班级经历；续班保留这一轮的完整结果。

原记录旁可以展示当前进展：原测评行仍是该次测评，旁边显示“秋季已报名”或“秋季等班”。新增报名不会把原测评记录移动走。

默认工作名单、本轮已处理记录、历史记录的范围要明确。视图和筛选按本轮需要整理，提供常用分类入口；每页专注本页字段，其他细节放在行下或学生详情。

同一人出现在多页代表不同工作事实。涉及统计时区分学生人数、联系次数、活动人次和报名单数。

## 9. 给执行 Agent 的开发顺序

### 第一步：确认现有能力与受影响入口

先读仓库 `AGENTS.md`、当前阶段入口和本任务相关的局部规则；记录实际施工分支、提交与已有工作树改动。本文的基线是定位参考，实施以实际工作树为准。

只围绕本轮涉及的能力列出“复用／重构／移除／补充”映射：行下详情、首联、邀约、测评、活动、分班、续班、学生记录聚合、通用跟进、权限及历史修订。

尤其核对两处：首联与跨阶段共用登记如何按新职责分工；“缴费确认学位”如何获得可靠业务依据。旧入口和旧数据兼容不列入开发前置任务。

### 第二步：先打通“测后未报名”的完整路径

用“测后未报名”验证整套方式：

**测评表行内操作 → 行下填分数和备注 → 需要时展开活动登记 → 保存留在原处 → 保存并下一位 → 学生页与活动页再读相同结果。**

同一条路径还要验证只写备注、无下一步、无联系日期也能保存。

这一增量先交付开发页面供产品负责人体验。重点确认连续录入是否顺手，以及“根据场景展开不同模块”的方式是否符合预期。

### 第三步：复用到其他工作现场

将已验证的登记模块依次接入首联、活动参与名单、分班和续班。

同步让学生入口能够按人速记、查看新体系产生的跨阶段记录。完成“沟通 → 首联”的职责调整和导航改名，整理受影响的路由、调用及测试，移除已被替代的旧逻辑。

### 第四步：补齐等班、退课与再次报名

保证学位、等班、正式班级关系分别清楚；退课有就地操作和原记录；直接导入在读学员能跟进；退课后重新报名保留前后两段经历。核对同课程、同学期再次报名的现有唯一性约束，给新报名提供新的业务轮次，保留原已取消的记录。

### 第五步：定向检查与交付

按第 10 节逐项核对，提交本任务的独立变更。交付时附上开发入口、完成范围、实际检查结果、待人工体验项和仍未完成的部分。

本轮核心完成范围包含表格就地登记、共用模块、学生聚合、首联职责调整、等班与退课接续。学生卡片布局可以后续单独交付。

## 10. 验收场景

每一项都要检查保存后刷新再读的结果，纯前端临时状态不算持久化完成。涉及权限或并发的项目进行对应定向验证。

| 编号 | 实际操作 | 预期结果 |
| --- | --- | --- |
| A01 | 测评行下只填家长反馈，下一步和日期均为空 | 可以保存；新增跟进记录；不自动生成待办或逾期状态 |
| A02 | 在测评行下填成绩、反馈，再展开活动确认参加 | 留在当前表；测评、反馈、活动结果各自保存并关联同一学生 |
| A03 | 连续处理不同阶段的两位学生 | 行下模块分别适配；课程、对象和上一位草稿不串到下一位 |
| A04 | 家长愿意测评，时间未定；之后再确认时间 | 先保存待协调邀约，再更新同一邀约；确认后进入测评预约名单 |
| A05 | 在学生入口登记在读孩子的微信反馈 | 使用与工作台相同的记录能力；无需回到首联或旧活动 |
| A06 | 对同一场活动先确认参加，后来登记到场；另参加第二场活动 | 第一场关系连续更新；第二场另有记录；沟通次数正确 |
| A07 | 家长表达报名意向；后来提供有效缴费确认；暂时没有班 | 意向阶段保留为意向；缴费确认后建立学位并等班；不自动建班或入花名册 |
| A08 | 等班期间记反馈，之后安排入班 | 等班学生始终可见；原反馈保留；正式班级关系正确建立 |
| A09 | 同一孩子本期在读，同时登记下期续班 | 两个期次分别处理；本期在读关系保持，续班结果关联下期 |
| A10 | 退出数学课，数独课继续上；之后重新报名数学课 | 只结束指定课程；退课、原学习历史保留；重报形成新轮次且能关联旧经历 |
| A11 | 从原获客批次、原测评表回看已经报名的孩子 | 原记录可见，当前进展可查；没有复制出多个学生档案 |
| A12 | 更正某次备注，再另记一次新沟通 | 更正保留修订链且次数不增加；新沟通追加一次；各入口再读一致 |
| A13 | 保存后该行已不符合当前筛选，再继续下一位 | 本轮行位置稳定，可回看；明确刷新名单后再整理范围 |
| A14 | 从调整后的站内菜单进入首联；完成首联后，从学生或测评现场继续登记 | 菜单与操作均指向新体系；首联职责清楚；后续跟进通过共用模块保存并可回看 |
| A15 | 直接导入的在读学生没有线索和活动记录 | 可在学生入口跟进、办理对应课程变动，所有记录关联到正确身份 |
| A16 | 重复点击保存、部分接口失败、其他人并发改动 | 不重复记录或报名；失败时保留输入并展示实际结果；冲突经服务端校验 |
| A17 | 不同权限用户从学生、测评、活动等入口操作同一类模块 | 可见范围与可执行能力一致；界面换入口不能绕过服务端权限 |

## 11. 实现边界与交付口径

本轮在现有表格和组件基础上实施，保留课堂、教学、财务及活动的专业操作能力。优先复用适用的 UI 和业务能力；受影响的学服页面、Server Action、RPC 与记录结构可以直接重构，RLS、权限校验和历史留存按新体系保持完整。共用模块按业务拆分，展示层分别接入表格或学生浮层。

阶段推荐采用少量清楚的事实规则；本轮不建设独立规则引擎、全新任务系统或营销自动化平台。

路由和内部结构按目标职责整理，同步全部受影响的站内引用；旧版本兼容边界见第 2 节。新体系产生的业务历史持续保留，各类事实保持各自权威来源，工作台维持表格。学生卡片视图按独立展示增量推进。旧 HTML 原型仅作讨论参考，录入交互以本文的表格与行下展开为准。

执行环境、数据迁移、生产发布与权限修改遵循仓库当前 `AGENTS.md` 和 runbook。**没有本次明确授权时，不进行生产迁移、业务写入、服务重载或发布。** 保护其他任务的工作树改动。开发检查通过、人工体验通过与生产发布分别报告，不代替用户关闭验收 Gate。[S1]
