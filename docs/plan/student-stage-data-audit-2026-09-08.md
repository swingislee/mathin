# 学员阶段数据校验 · 2026-09-08

> 结论：当前 4,142 条“待首联”不是可信的待首联人数。已完成全量只读关联校验；本轮交付审计结果，页面归类尚待修正。

## 范围与口径

本机开发数据库快照时间为 2026-09-08 01:31（Asia/Shanghai）。校验覆盖 5,515 个当前系统主体、14,566 条来源记录，以及沟通、预约、测评、报名、班级成员、课程机会和跟进备注。另对全部 5,515 个主体逐一比较列表索引与个人快照。

系统主体包括 Student 和未关联 Student 的 Lead。身份键不重复不代表实际人员已去重；来源位置和花名册行数也不等于独立人数。源表优先级沿用 [更新源表交叉整理](../runbooks/source-reconciliation.md)。旧魔法校的“在读／历史”标签仅作交叉证据，当前在读情况同时核对日期和业务主来源。

## 待首联的逐人分组

4,142 条由 1,249 个 Student 和 2,893 个未关联 Student 的 Lead 组成。以下按证据优先级互斥分组，每条只计一次：

| 核对到的证据 | 主体数 |
| --- | ---: |
| 已有报名业务记录 | 340 |
| 另有花名册在班经历 | 508 |
| 已有到访或测评参加记录 | 107 |
| 已有续报、报名或退费来源 | 57 |
| 已有活动或预约记录 | 191 |
| 已有沟通记录，联系结果未结构化 | 1,475 |
| 目前只有未接通或号码无效记录 | 401 |
| 尚未定位到后续业务事实 | 1,063 |
| 合计 | 4,142 |

340 条报名对象中，238 条直接关联 Student，102 条通过同一源行的明确业务关联定位到 Lead；报名记录均缺少结构化期次。审计不会依据同名同电话，把源行改挂到另一个身份。

“尚未定位到后续业务事实”表示当前资料不足，不能证明从未沟通过。“联系结果未结构化”也不表示未联系。含多项证据的对象只进入上表最靠前的分组。

## 确认的问题

1. **列表和个人快照使用了不一致的归类口径。** 全名单有 240 条阶段不一致：238 条在列表属于待首联、个人快照属于历史学员；另有 2 条在列表属于待报名、个人快照属于历史学员。列表索引对 `course_enrollments` 内连接 `school_terms`，遗漏了缺少 `term_id` 的真实来源报名。个人快照的“曾报名”判断没有这个连接条件。
2. **报名来源尚未关联 Student 时没有进入名单的报名判断。** 部分课程机会已关联 Lead，同源的报名记录仍然只有来源 ID。以 `student_id` 为唯一入口会漏掉这些报名事实。全库另有 177 条报名记录无法通过当前明确关联定位到任何名单主体，继续保留为归属待核对记录。
3. **主阶段把资料缺项当成了待首联。** 已有活动、到访、在班来源或沟通备注，但缺少 `connected/declined` 的记录会落入默认待首联。有效首联规则适用于新流程，不能据此否定导入前已经发生的经历。
4. **“历史学员”也不能仅从缺项推导。** 个人快照虽然识别了部分既往报名，但仍依赖结构化期次判断当前有效关系。当前历史学员 30 条中，有 2 条在参考花名册中存在结束日期尚未到期的在班记录，需和最新业务来源核对。应先确认当前课程关系和结束依据，再决定在读／历史归类。

当前模型中的 `record_state='current'` 表示可继续使用的业务记录，不能单独证明所属课程仍处于本期；来源报名允许缺少课程、期次和时间，不能把这些缺项当作已结束。

## 其他需要核对的资料

以下为交叉标记，可互相重叠，不与上表相加：

- 待首联中共 738 个主体有花名册在班经历，其中 25 个在参考资料中有结束日期尚未到期的在班记录，25 个存在在班记录但未能取得有效结束日期。
- 待首联中 1,500 个主体存在联系结果为空的沟通记录；其中部分已被上表更后续的证据优先归组。
- 全名单 34 个未关联 Lead 与现有 Student 存在相同姓名和完整电话候选，其中 11 个位于待首联。它们是身份核对候选，尚未据此合并。
- 37 条来源记录连接到多个当前系统主体；待首联中 21 个主体涉及这些来源。缺少明确主体的业务记录遇到多主体来源时，审计保持未归属。
- 待首联中 385 个主体缺少可直接使用的联系电话；号码为空、不完整或已在来源中打码的记录需要补充资料。

## 交付与复核

采集入口为 `scripts/student-stage-audit.mjs`，分析与报告入口为 `scripts/analyze-student-stage-audit.mjs`。目标核验复用现有本地主机、实际 Supabase origin、监听进程、Docker 网络与数据库指纹检查。采集在 `REPEATABLE READ / READ ONLY` 事务中执行。

逐人 JSON、列表／快照差异和可筛选 HTML 报告保存到 gitignored 的 `.tmp/student-stage-audit/<批次>/`，包含每个人的业务记录 ID、来源 ID、核对分组及候选标记。HTML 只展示姓名和打码电话，可按阶段、校验分组、姓名、电话尾号或阶段矛盾筛选；来源值通过 `textContent` 展示。共享仓库仅保存本摘要与审计代码。

已核对互斥分组总数为 4,142、报告覆盖 5,515 个主体、嵌入数据可解析和报告脚本语法有效；完成全量列表／快照比较。HTML 视觉未由浏览器代验。本轮保持学员、身份关联、业务事实和生产环境原值。

后续修正需要统一阶段事实入口，补上来源报名及花名册关联，区分“有明确后续经历”和“资料不足”，按当前课程证据确认在读／历史，再重新计算待首联人数。当前审计结果不能直接充当批量改阶段或合并身份的名单。
