## 1. 这次反馈要求解决什么

四张反馈截图是同一位对象在不同填写状态下的详情：尚未选择本次结果、已沟通、号码无效、暂缓／下次联系。它们应该是同一个跟进面板的状态变化。

目标是：**以同一个人为主体，使用同一套背景加载、草稿编辑、业务模块、保存和历史读取规则；页面入口只提供当前业务上下文与推荐操作。**

本合同细化产品负责人在 2026-09-06 提供的升级规划中“表格与行下详情”“共用快捷登记”“一次提交、各处一致展示”的要求，不重排整个学服升级阶段。

需要一起解决四类问题：

1. 表格主行与详情承担不同职责，减少重复输入及状态歧义。
2. 联系结果变化时，核心输入区、动作含义与保存位置保持一致。
3. 跨入口复用同一份身份、事实、记录与模块逻辑，不只复用外壳样式。
4. 保留白色普通行和圆点状态表达；当前行及详情采用浅黄色填充、深黄色描边，并区分勾选、展开与焦点，适应普通笔记本。

## 3. 三种数据语义分别呈现

| 层次 | 含义 | 加载和编辑规则 |
| --- | --- | --- |
| 已保存事实 | 已加微信、当前邀约、最近一次联系、当前课程等 | 读取权威记录；以只读背景或明确的“更新该事项”模块呈现 |
| 本次跟进草稿 | 这一次新发生的情况、沟通及业务变动 | 默认新建；本次结果和备注为空，或恢复本人的未提交草稿；选择字段只修改草稿 |
| 历史修订 | 刚才记错了，需要修改某一条记录 | 从历史中的“修改这条记录”进入，带记录 ID、版本和原始值，保留修订痕迹 |

具体约定：

- “最近跟进”用于已保存摘要；“本次联系结果”用于本次录入，不再共用一个标签和回退值。
- “沟通摘要”和“备注”是同一份记录内容；界面统一称“备注”。行内短输入和展开后的多行输入是同一字段的两种呈现，不建立第二份摘要，不重复写记录。
- 已有微信事实正常显示；“本次未确认”表示此次未更新，不等于“尚未加微信”。意向资料也区分未更新与明确修改。
- 已有邀约加载原事项，更新同一邀约；另约其他场次才新建相应事项。
- 单独写情况不需要先选联系结果、下一步或日期。只登记业务结果时，备注也可以为空。
- “号码无效”描述本次所用号码／联系渠道，不自动否定对象身份、既有微信或其他课程关系。
- 新增一次联系与修订旧记录使用不同动作。一次联系附带多个业务结果，沟通次数仍计一次。

## 4. 主行与面板的职责

### 4.1 主行：识别、浏览与快捷填写

保留姓名与必要识别信息、本页关键事实、最近已保存摘要和更新时间。提供易找的“记情况”及当前阶段最常用的 2～3 个业务操作，其余放入“更多”。

依据本次“未接通”反馈，姓名和联系结果保留在主行，行下详情不再复制一行姓名、“最近沟通”选择器或最新结果／时间。主行结果控件接入共享草稿与提交控制器；字段不必移进详情，才能实现共用。

备注采用一份内容、一个当前编辑位置：折叠时可以在主行快捷输入；展开时在详情提供多行编辑，原行内输入切换为简短的展开提示，不同时保留两个可编辑框。收起后回到同一字段的短输入，不丢内容或另建记录。行内保存与面板保存若同时存在操作入口，应指向同一次提交；展开时集中保留面板提交按钮，减少重复动作。

有未提交内容时可显示“有草稿”；主行事实及“最近更新”在服务端保存成功后更新，不能把未保存结果当作业务事实。

### 4.2 共用面板：备注、业务登记、一次保存

面板有稳定的内容次序。下面是结构示意，不是已经交付的视觉稿：

```text
主行：对象标识 │ 本页事实 │ [未接通 ▾]  备注已展开 │ 最近更新
└─ 补充填写（极浅黄；与主行共用一圈深黄色外轮廓）
   备注                                                    [收起]
   [同一份备注的多行编辑区，始终可用]
   下次联系（可选） [日期与时间 ▾] [清除]
   提交提示                              [保存] [保存并下一位]
   ▸ 历史记录
```

- 上图仅展开“未接通”的最小补充内容；其他状态可增加实际需要的业务模块，备注、提醒与提交区保持相邻且顺序稳定，不为暂时不存在的字段预留空栏。
- 嵌入主行下方时直接从补充字段开始，姓名、电话、联系结果和最近更新时间由主行提供。完整来源信息进入背景／历史。学生浮层没有可见主行，外层补充必要身份与联系控件；仍使用同一字段和控制器。必要的无障碍区域名称保留，但不为此额外显示一行重复标题。
- 页面操作可以直接展开对应业务模块并定位它；备注输入始终可用，面板骨架及保存规则保持一致。业务模块需明确当前活动、测评、课程或期次，并保留适用的圆点进度。
- 联系结果是实际联系的登记字段，不是整个面板的开关。教师观察、现场反馈等速记使用合适的记录类型，不强迫选电话结果。
- 备注与提醒各有一个编辑位置。提醒位于备注正下方，左边缘对齐；触发按钮按日期文本定宽／自适应，普通笔记本先以约 `14–18rem` 为原型尺度，容器较窄时不溢出，英文与完整日期不截断。该范围是布局起点，不是固定像素验收门。
- 提醒空值显示“选择提醒时间”，标签标明可选；选定后展示完整日期与时间并可清除。详细说明就近按需提供，不拉成一条贯穿表格的说明／按钮带；提醒仍随本次统一提交，不增加独立“保存提醒”流程。
- 联系提醒与测评／活动预约时间是两种事实，分别标注。提醒的适用条件由业务模块和服务端共同校验。
- 历史默认折叠；展开后可修订指定记录。新建与修订有明确模式提示。
- “保存”成功后留在当前行；“保存并下一位”在有连续名单的入口出现，全部必要提交成功后再前进。浮层没有队列时保留普通保存。

### 4.3 联系结果变化时，哪些可以改变

| 本次结果 | 核心保持一致 | 允许变化的业务内容 |
| --- | --- | --- |
| 尚未填写 | 情况输入、可选提醒位置、模块入口、保存区、历史 | 可先速记；按实际选择展开业务，不借用上次结果伪装本次已选 |
| 未接通 | 同上；选择本身不保存 | 可以记录尝试及下次联系；既有身份、微信等事实继续保留 |
| 已沟通 | 同上；选择本身不保存 | 可更新本次确认的资料、意向、邀约等事项 |
| 暂缓／下次联系 | 同上；选择本身不保存 | 可登记暂缓原因与可选提醒；不自动取消既有邀约或报名 |
| 号码无效 | 同上；选择本身不保存 | 记录号码问题；其他渠道和业务事实继续可查看。依业务条件处理号码或渠道，不自动安排重拨 |

切换结果时保留已填写的其他模块草稿。与当前结果不兼容的变动显示解释，允许调整或明确选择“本次暂不提交该项”；保留暂不提交的草稿，不静默写入矛盾结果，也不静默丢弃。

圆点继续表达邀约协调等模块内真实的当前步骤和完成情况。联系方式、联系结果、资料事实与协调进度分别表达，避免用一个大色块代表所有状态。

## 5. “加载一致、逻辑一致”的具体边界

一致性的比较条件是：**同一对象、同一业务事项、同一权限和可见范围。** 不同课程、不同活动或不同权限本来就可能产生不同的可用字段，面板应解释对象及权限差异。

### 5.1 入口传上下文，共用加载器读事实

入口传入稳定的 `leadId`／`studentId`、相关测评／活动／报名 ID、优先展开模块以及可选的队列信息。入口不自行拼一份“该学生状态”，也不决定某个结果是否自动提交。

共用上下文读取包含：

1. 正确身份及已有线索—学生关联，当前正在操作的业务对象。
2. 已保存事实、当前有效事项及服务端版本。
3. 当前角色允许查看和执行的模块与限制原因。
4. 最近记录及完整历史的分页入口，统一事件 ID、作者和服务端发生时间。

名单筛选、工作日期与分页只决定本轮处理哪些行；打开跟进面板后，人的背景由稳定身份加载。查看某日登记时可以过滤历史，但明确显示过滤条件，不将当日片段当作完整历史。

身份聚合优先复用 [Student360 的身份约定](../../src/features/school/student-360-contract.ts) 与 [授权读取](../../src/features/school/actions/student-360.ts) 中适用的能力。现有读取需要评估、适配，不视为已经提供完整编辑上下文。首屏读取必要事实及最近记录，完整历史按需加载，不为每一表格行预取全部档案。

同一学生有多条线索或多个业务对象时使用实际关联；遇到不能唯一确定的事项，业务模块要求选择。单独速记可以只关联明确的主体，不能按相同姓名或手机号擅自合并身份。

### 5.2 草稿共用，业务对象不串用

- 共用草稿控制器管理本次情况、联系结果、可选提醒和各业务模块，不由每个入口复制一组状态。
- 草稿按当前用户、主体、业务上下文及登记会话隔离；相同上下文重开可恢复，另一位学生或另一门课程使用自己的草稿。
- 切换模块、折叠面板、切换行时保护输入；明确放弃才清除。离开页面时有未提交内容的保护。
- 加载中、加载失败、无权限、空历史及保存中使用同一套状态表达。加载未完成时不把未知值当成“没有记录”，也不提交缺失上下文。
- 后台刷新不覆盖已修改字段；检测到事实版本变化时提示核对，保留输入。
- 保存成功后刷新相关事实与列表摘要；继续未完成模块时，已成功部分不再次当作新草稿提交。

### 5.3 一次保存，多个业务结果

共用面板提供一个提交入口，协调本次情况和已修改、已纳入提交的业务模块。

- 仅展开且未改动的模块不校验必填、不提交。不完整的已修改模块提示补齐或明确暂不提交。
- 同域关联写入优先采用事务；确需分步提交时，结果列明成功与失败，保留失败草稿，重试只处理尚未成功部分。
- 提交使用防重标识，阻止重复点击，并支持安全重试。记录 ID、发生时间和版本来自服务端，刷新后的显示与当场反馈一致。
- 全部必要内容保存成功后才执行下一位。成功行在本轮名单中保持位置，主动刷新、切换视图或分页时再按最新筛选整理。
- 服务端重新校验权限、业务状态和需要检查的容量，冲突保留输入并给出处理办法。
- 同一份跟进事实有一个权威来源；联系、测评、活动、报名各自保留业务记录与关联。统一面板不等于把全部专业记录塞进一张表。

当前 [学生跟进 Action](../../src/features/school/actions/followups.ts) 只接收学生身份；[线索联系 Action](../../src/features/school/actions/leads.ts) 及相应 RPC 要求联系结果并有提醒适用条件。要兑现“线索和学生都能只写备注”“跨模块一次保存”，需要统一读取与提交合同、补齐身份支持，不能仅抽取前端组件就宣称完成。

## 6. 表格强调方案、设计依据与笔记本布局

### 6.1 理论与成熟实现的参考

以下为 2026-09-06 查阅的公开来源。借鉴的是状态划分和视觉组织方法，颜色取值仍遵循本项目主题；这些来源不构成对本页面美观或可用性的验收。

| 依据 | 来源中的原则／实现 | 本项目的设计推导 |
| --- | --- | --- |
| 视觉层级 | 注意力受对比、尺寸和分组共同影响。[NN/g：视觉层级](https://www.nngroup.com/articles/visual-hierarchy-ux-definition/) | 大片填充和超长时间按钮的视觉重量过高；缩小强调面积与无效空间，比单独换色更重要 |
| 共同区域与邻近性 | 同一边界会形成强分组；过度框选又增加杂乱。[NN/g：共同区域](https://www.nngroup.com/articles/common-region/) | 当前主行和详情共用一个轮廓；内部靠对齐和间距分组，备注与提醒就近排列 |
| 渐进展开 | 展开区用于补充信息；选择与展开是不同表格能力。[Carbon：数据表用法](https://carbondesignsystem.com/components/data-table/usage/) | 展开区去掉主行已经完整表达的姓名、结果和时间，直接提供补充填写 |
| 状态分层 | Carbon 区分悬停、焦点、选中、展开；Ant Design 分别提供 `rowHoverBg`、`rowSelectedBg`、`rowExpandedBg`。[Carbon：数据表样式](https://carbondesignsystem.com/components/data-table/style/)、[Ant Design：Table tokens](https://ant.design/components/table/#design-token) | 勾选、展开、当前处理对象和键盘焦点分开建模，不再让它们共享一个选中色规则 |
| 色阶用途分工 | 轻背景、组件背景、边框和文字使用不同色阶。[Radix Colors：色阶用途](https://www.radix-ui.com/colors/docs/palette-composition/understanding-the-scale) | 极浅黄负责区域归属，深黄负责轮廓，正文保持墨色；不给填充、边框和文字使用同一亮黄 |
| 焦点与状态可辨识 | 键盘焦点与选中需可区分；必要的状态提示需有足够对比。[WAI：Focus 与 Selection](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/#kbd_focus_vs_selection)、[WCAG：非文本对比](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) | 保留独立焦点环、勾选标记和展开箭头，浅黄色不作为唯一识别手段 |

### 6.2 强调什么，才决定用什么视觉手段

| 状态／信息 | 需要传达的含义 | 建议表现 |
| --- | --- | --- |
| 普通行 | 浏览和比较数据 | 白底、稳定行线及清楚的文字层级；不额外加斑马底色 |
| 悬停行 | 帮助横向对齐阅读，即将操作 | 比选中更弱的短暂暖色反馈，移开即消失；不出现粗边框 |
| 批量勾选 | 该对象属于本次批处理集合 | 明确勾选框＋轻微整行暖色；详情不因此获得强描边 |
| 仅展开详情 | 正在查看该行的补充信息 | 展开箭头＋极浅黄补充表面及轻结构线；展开本身不等于批量选中或正在编辑 |
| 当前正在处理的行 | 目前操作属于这一个对象 | 主行轻黄填充，主行与其详情共用一圈深黄色细描边；详情底色更轻，不铺同强度的实色 |
| 键盘焦点 | 下一次键盘动作作用于哪里 | 焦点所在控件或可操作行有独立、清晰的焦点环；移动焦点不改变勾选集合 |
| 业务状态／圆点进度 | 未接通、邀约待确认、号码异常等实际事实 | 在对应字段用圆点、文字或紧凑标签表达；不按业务结果把整个对象染成另一种背景 |

同一行同时处于勾选、展开、当前处理和焦点状态时，保留各自的标志；背景选择一套确定的结果，不叠加多个半透明色层。悬停不覆盖当前处理的边线，当前处理的强调也不吞掉焦点环。

实现应拆分业务状态、批量选中、当前处理对象、展开状态及 DOM 焦点。样式使用各自的状态标记；ARIA 按实际组件语义设置，不用 `aria-selected` 作为所有强调的统一开关。

### 6.3 本项目方案：极浅黄填充，深黄轮廓，白色输入

这次用户明确要求整块蓝色区域改为浅黄色填充与深黄色描边；此前“详情保持纯白、只加左侧细线”的建议被此方案替代。关键是填充强度和范围，而非照搬蓝色方案的强度换一个色相。

- 普通行与表头继续使用白色 `--card`。当前主行及详情从 `--moon` 与 `--card` 派生低饱和浅黄色，主行略明确，详情更接近白色；两者通过一个连续外轮廓表达归属。
- 深黄色描边的“深”指足够暗、可辨识的琥珀／土黄色，不是高饱和亮黄。集中在当前处理对象的外缘，不给每个单元格、每个内部模块都加深黄框，也不叠加第二圈卡片边框。初始原型按细描边处理，最终粗细与对比由实际页面核对。
- 内容、输入框和按钮保持正常不透明度。浅色输入使用白底及清楚的墨色文字，让编辑控件与浅黄色区域易于区分；不以降低父容器透明度达到柔和效果。
- 黄色只表示当前处理范围，不暗示“有警告”。真正的异常有明确图标／文字；圆点进度及品牌主动作各自保留语义，避免每个普通状态选择器再铺满一种强调色。
- 原有多个彩色实底按钮优先评估为中性控件＋局部状态点／文字，仅当前选项或需要注意的事实增加适量强调。正常文字和禁用文字的对比区分明确。
- 深色模式采用星夜卡片上的低亮度暖色表面及暖金轮廓，输入保持深色不透明表面；单独定义深色 token，不把浅黄大面积原样搬入暗色页面。
- 必须用于识别状态的标记与相邻颜色按 WCAG 非文本对比要求核对；淡黄填充只是补充提示，不要求靠把整块背景加深来承担全部可辨识性。键盘焦点另行核对。

色阶集中在主题层按用途定义，例如行悬停、批量选中、编辑行、详情表面、编辑轮廓，组件使用语义 token。沿用 [设计系统](01-design-system.md) 的基础色，参考外部体系的方法而不引入整套默认蓝色或新的 UI 框架。

### 6.4 容器宽度优先，减少移动视线

- 优先验收 `1366×768`、`1440×900`，同时考虑侧栏占用及浏览器缩放。断点依据面板实际宽度，不只依据整屏宽度。
- 本次情况与保存动作不因联系结果切换到不同栏；通过纵向顺序承接动态模块，不用大空白撑齐两个无关区域。
- “未接通”详情按内容自然收缩：备注、短日期控件、提交、折叠历史构成一个紧凑补充区。删除重复内容后同步收回高度，不保留原先空置栏和最小大高度。
- 提醒控件不使用横向 `flex-1` 撑满剩余宽度。备注需要较长阅读宽度，日期只需要容纳完整日期和时间，二者不要求等宽。
- 普通笔记本默认以连续主内容区为主。只有业务模块内容确实适合并排且容器足够宽时才分栏，宽屏不把备注挤到很窄的最右侧。
- 选择项完整显示文字，优先自适应宽度及换行；“暂缓／下次联系”“尚未加微信”等关键文案不以省略号作为常态。
- 不为塞入更多按钮压缩正文。次要说明就近放置；长来源信息进入背景或历史，不反复占据面板主体。
- 圆点进度按业务先后横向呈现，空间不足时允许整体合理换行，保留每一步的完整含义。
- 长面板的提交区可在所属滚动容器底部保持可达，同时预留内容空间；验证它不遮住输入、历史或系统弹层。
