## 1.37 秒之外的成本

承接[用户 HAR 与获客别名诊断](overview-first-load-har-20260921.md)。前轮 3.01 → 1.37 秒是四次获客 SQL 的合计，不是浏览器整页耗时；即使每页别名只聚合一次，四页仍各自扫描、选择最新来源、检查 RLS、生成 revision。

本轮读取实际 `getStaffOverviewData`、工作单和目标值，使用固定本地管理员与真实 Supabase HTTP。前轮窗口聚合已应用时，完整读取仍有 **42 次 REST 请求，约 8.85 MB 内部 JSON**。其中获客四次串行约 2.27 MB，沟通五次约 3.13 MB，线索约 1.08 MB，报名约 1.06 MB。这些是服务端与数据库间的数据，不是浏览器下载量。

两次基线中，最后一个数据响应结束后，应用聚合约需 144–170 ms。月目标读取在本轮修正月份时区的对照中为 5–10 ms，不是主要等待。统计总览仍有读取完整事实再计算的结构，缩短 SQL 不等于已消除该负担。

另外，用户 HAR 有 155 次预取。生产网关在 HAR 对应的 17:33:01–17:33:10 窗口有 59 次 `/auth/v1/user` 请求；该日志窗口可能含其他用户和后台任务，不作为单请求精确链路。代码及本地逐请求追踪确认：页面预取也经过代理鉴权。原侧栏每个可见 Link 都默认参与自动预取。没有通过跳过鉴权来提速。
