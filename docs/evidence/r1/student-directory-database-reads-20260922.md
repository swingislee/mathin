# 学生名录：批量权限与数据库卡片读取

状态：**两条迁移已应用本机开发库，应用已接入；机器检查通过，待用户验收，生产未发布。** 保持 R1-Live-2，未验收生产整页 1 秒可操作。

## 根因与本次改动

[前轮诊断](student-directory-read-diagnosis-20260921.md)确认两条遗漏路径：管理员每页 100 人逐人重建完整档案；教师仅返回 5 人，也逐条判断数千名学生的权限。此前沟通页的批量权限优化作用于另一个读取函数，名录没有接入；已有分组优化仍在。

本次同时修改数据库内部和应用读取合同：

1. `student_record_index_for_population` 在一次查询内复用批量可见集合，替代逐人权限调用。名录提前排除纯线索，报名事实按候选身份限制；原共享索引保留完整人口范围，继续供其他入口使用。
2. `student_directory_page` 在数据库内完成权限、范围、筛选、分组、计数、排序和分页。全部候选保持数据库行，取消数千人先汇总 JSON、再拆回行的中间步骤；协作信息只在负责人／业务组分组时读取。
3. `student_directory_card_rows` 批量补齐当前页卡片：姓名、年级、电话尾号、阶段、分组、真实测评和可办理标记。名录不再调用完整档案及学习背景读取器；选人进入沟通继续使用原完整 RPC。
4. 两个私有读取器内部的五类业务视图改为查询内共享来源集合，复用来源有效性、归档与人工重新启用判定。中间版本一次管理员查询约 12,098 次来源有效性调用降到 1,353 次；剩余调用来自共用报名事实，重复样本约 6 ms。公共视图、RLS、业务写入口保持不变。
5. 页面改调 `list_student_directory_cards`，按卡片 schema 校验；接口错误不回退到昂贵的完整档案查询。

这是查询内批处理，没有跨请求缓存或异步刷新窗口。权限撤销、历史归档及重新启用在后续查询立即生效。未新增索引、物化表或业务列，未改写正式业务记录。
