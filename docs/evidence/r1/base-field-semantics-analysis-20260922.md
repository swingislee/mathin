# Base 宽表语义与生产名单只读核查 · 2026-09-22

状态：分析完成，业务模型待确认；本轮只读核查，未修改应用、开发或生产业务数据，未部署、未重启。此报告补充并限定此前“联系状态同步”修复的结论，不代表用户业务验收或阶段关闭。

**核心判断**

这张获客总表是一份持续维护的客户运营档案。一行同时承载身份、获客、首次确认、后续跟进、项目运营和当下状态。导入时，需要分别回答“这是哪个人”“哪些事情确实发生过”“现在需要做什么”。当前实现把这几个问题混在一起，导致字段保存正确、业务事实和工作名单仍然不可靠。

9 月 20 日获客总表共 3,859 行，其中 3,755 行有业务内容，原始结构包含 41 列：40 个业务字段和 1 个自动登记日期。生产来源档案覆盖全部 3,859 行，逐行非空业务字段内容哈希全部一致；现有沟通记录没有挂在内容不匹配的旧版本上。这说明本次主要问题发生在原始资料之后的转换与查询层。

用户已确认：不同人员对“跟进信息／跟进结果／跟进日期”的填写方式不一致。因此，不能将这一组字段普遍解释成固定的一次沟通，也不能推定每次导出变化都代表新增了一次沟通。

**1,703 条推断记录需要怎样理解**

其中首次确认结果为空的有 1,082 行，写“暂无结果”的有 617 行，还有 4 行的多选结果存在相互冲突的解释。94 行在首次确认、跟进和项目沟通备注中均没有文字。247 行首次确认备注包含“未接／未通／无人接／空号／停机”等词；这是优先核对的线索，不能仅凭关键词自动判定整段备注的意思。

不能把这 1,703 行全部改成“未联系”。其中可能存在真实沟通，只是结构化结果没有填写。需要区分：原表明确事实、备注中可证实的事实、系统推断、来源冲突与未知。统计报表采用的确认规则可以单独保留，但不应再反向生成一次已经发生的联系。

上一轮处理把已有沟通和到访投影同步为 `contacted`，修复了原状态未同步的问题；对这些沟通投影本身的语义审查不充分。因此，上一轮 2,771 条状态更新不能被解释为“逐条验证了 2,771 次真实联系”。本轮发现要求先复核输入事实，再决定是否调整阶段，不能继续只修标签。

**“最近一次”还有独立的确定性错误**

生产中有 1,006 条线索拥有多条沟通记录，只有 150 条拥有至少两条完整日期的记录。沿当前线索读取顺序，46 条会选到早于另一条已知日期的记录；310 条在已有带日期记录的情况下，选中了没有日期的记录。

基础线索读取使用记录 ID 降序作为空时间后的次序，阶段事实函数使用 ID 升序作为次序。这两种排序会让 507 条线索选出不同的联系结果；该数量表示候选结果不同，不等于 507 人的主阶段必然不同。阶段推导还会查看是否曾经有效沟通、到访、测评或报名。

日期需要保留原始精度。“11.13”是月日，“11 月”是报表周期，自动登记日期是填表时间。它们不能补造成同一个完整业务时间。原表中 51 行的跟进日期月份与跟进月份选项不一致，也说明“报表月份”和“实际日期”要分别保留。

“没有找到沟通事实”最多说明资料不完整。对过去已运营的学生，直接翻译成“现在待首次联系”，会生成大量不合业务实际的工作项。

**重复、版本与身份需要分开核对**

- 当前 Base 内有 253 组同名同电话的来源，共 523 行；这些可能是重复登记、再次获客或长期运营资料，不能仅凭行重复就删人或删历史。
- 生产来源档案中，获客表保留了 264 条额外版本和 2 条不在最新文件中的旧来源。所有最新行都有内容相符的档案；现有沟通没有挂到不相符的旧版本。这些版本数量不等于重复客户数量。
- 生产 Lead 内没有查到完全同名同电话的重复键，但 Lead 与 Student 之间有前述关联缺口。只查一张表的唯一键不足以证明业务身份一致。
- Base 中有 146 行学员有称呼而没有可识别完整号码。昵称相同、缺号码和家长共用号码时，应结合学校、年级、已有归属和到访证据核对，不直接合并。
- 到访表 854 行中，解析出学员姓名的有 710 行；仅 239 行可用完整姓名和号码与获客表精确匹配。这不是其他行全都匹配错误，而是说明跨表连续性不能只依靠精确同名同号规则。

此前“生产固定读取 9 月 7 日来源”指总览获客取数入口曾按旧文件筛选，相关修复已在 [9 月 21 日增量来源记录](overview-acquisition-incremental-production-20260921.md)说明。原始行保留旧来源版本标签，并不表示最新内容没有导入。本轮全部最新行内容一致的结果进一步排除了这一解释。

**建议先确认的目标逻辑**

| 业务对象 | 建议规则 |
| --- | --- |
| 客户与学生身份 | 一个已确认的学生身份汇总获客、沟通、到访、报名等事实；来源行与身份关系保留确认／待核状态 |
| 获客 | 保存来源行、渠道、区位、获取人员、时间和多次获客记录；不要因已有沟通而丢失来源 |
| 首次确认 | 单独保存原始结果和备注；人员、组别、月份用于归属与统计，不能单独证明有效联系 |
| 跟进 | 在填写方式不统一时先作为来源跟进摘要；只有证据能够区分事件时，才生成独立沟通记录 |
| 当前快照 | 微信、诺访、意向等保留当前值、来源和适用时间；与某次历史沟通中的状态分开 |
| 袋鼠等专项 | 保留项目类型、沟通人、参与情况、开团及领取信息；避免写入通用首联和课程报名 |
| 当前负责人 | 确认人员作为学服负责人来源依据；已明确调整的生产归属保留，冲突沿现有核查字段标记 |
| 阶段老师 | 测评、授课等阶段分别确定实际老师；学服兼任测评时可同时承担学服与阶段老师 |
| 分组 | 当前筛选使用已指定的学服组成员；历史获客组、确认组、跟进组各自保留，不能互相覆盖 |
| 当前待办 | 根据当前工作范围、真实业务事实及下一步动作产生；历史未知资料进入核对范围，不自动生成“待首联”工作 |
| 统计 | 人数、来源条数、已证实事件数、来源报表确认量分别命名；报表规则不能反向制造业务事件 |
| 问题标记 | 沿用已有来源关联、字段 `review` 和业务备注机制；记录原值、推定依据、冲突或缺项，避免另建互不兼容的标注口径 |

原表已有 124 行的获客组和确认组不同，74 行的确认人员和跟进人不同。这些可能是转交或协作，应保留各阶段责任人，不应全部压成一个“负责人”覆盖过去。

**后续修正顺序，仅为方案**

1. 先确认 41 个字段的业务含义，尤其是“暂无结果”、跟进摘要、专项活动与当前状态的边界。
2. 在独立预览中给每条来源标明：原始事实、可确认事件、推定、冲突、未知；保留最新及历史来源版本。
3. 先修身份关联和页面资料补齐，再复算阶段与工作范围。单纯改 `status` 会继续掩盖两套身份或两套名单的问题。
4. 对推断联系、阶段冲突、同名无号等生成明确的待核清单；人工确认一批，再形成可回退的生产增量。
5. 后续导入增加语义预检：新增／更新来源不能自动等于新增事件；检查枚举值覆盖、日期精度、冲突选项、跨表身份、当前与历史范围及专项归属。预览需要同时显示原始字段差异和将改变的业务阶段。

本轮未形成生产应用清单，不申请部署；保留当前生产状态，供业务模型核对。
