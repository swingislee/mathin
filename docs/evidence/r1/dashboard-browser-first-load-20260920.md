- 生产目标为 `https://mathin.club/zh/dashboard?view=overview`，默认本月／当前周期，桌面视口 1440×960。只读 preflight 确认服务器为 Xiaomi，应用 `current` 与运行进程目录一致，Supabase origin 为 `https://supabase.mathin.club`。
- 生产应用仍为 `1eaab0fbe3285d44f89924b8c1f771c5417ef657` / release `20260920-005221`。此前 Storage 传输候选 `f4fd984c` 未部署，本轮没有应用发布、迁移、权限调整、业务写入或服务重启。
- 账号名称中的“管理员”不代表其生产授权：本轮授权账号的生产 `profiles.role=staff`，账号有效，但 `followup.view=false`、`student.view.all=false`。因此本记录不能当作正式管理员权限上下文的基线。

## 浏览器结果

硬刷新使用 CDP `Network.setCacheDisabled(true)` 与 `Page.reload(ignoreCache=true)`；普通刷新恢复缓存。按硬／普通交替测量三组，6 个 `performance.timeOrigin` 均不同，没有重复读取旧文档。

数据呈现指标为首个 `[data-overview-scope="period"]` 区域具有可见尺寸后再等待两个动画帧。它表示数据区域出现，不表示所有业务按钮已经逐一完成交互验收。首个内容绘制和较早的 LCP 不能替代该指标。

| 样本 | 刷新 | 首字节 | 文档响应结束 | 数据区域出现 |
| --- | --- | ---: | ---: | ---: |
| 1 | 硬刷新 | 0.749 秒 | 8.691 秒 | 8.746 秒 |
| 2 | 普通刷新 | 0.828 秒 | 8.863 秒 | 8.893 秒 |
| 3 | 硬刷新 | 0.874 秒 | 8.742 秒 | 8.783 秒 |
| 4 | 普通刷新 | 0.899 秒 | 8.845 秒 | 8.875 秒 |

| 6 | 普通刷新 | 0.944 秒 | 8.741 秒 | 8.773 秒 |

补测“今日工作 → 数据总览”三次，以真实点击事件至数据区域显示计时，分别为 **7.864、8.515、8.498 秒**。本次账号在普通刷新及重复侧栏切换中也慢，不能将它归为仅首次发生的冷启动。

资源对照：

- 硬刷新脚本最晚在 0.961–1.070 秒到齐；普通刷新在 0.835–0.952 秒到齐。
- 首个内容绘制为 0.860–1.060 秒；采样期间没有记录到超过 50 毫秒的主线程长任务。
- 硬刷新文档及已完成资源传输约 1.68–1.79 MB，普通刷新约 70–112 KB；传输量显著减少后，数据仍在约 8.8 秒出现。字体和脚本体积仍有优化空间，但不能解释本轮主要等待。
- 六次浏览器网络样本的 HTTP(S) origin 均为 `mathin.club`，总览核心服务端读取没有调用 Storage。此前 2.8 秒的 Storage 运维 HEAD 异常，不能解释本轮捕获的数据库等待。

## 数据库证据

浏览器刷新期间，每约一秒采样一次 `pg_stat_activity`。四条查询连续执行至 7.37 秒，`wait_event_type` / `wait_event` 为空。随后通过参数化的 `pg_stat_statements` SQL 形状确认来源为：

- `leads`：线索目录；
- `operational_leads`：当前运营范围；
- `lead_source_records`：线索来源；
- `business_lead_communications`：沟通事实；
- 同一时段还观察到 `course_opportunities` 读取。

以相同账号的声明、`authenticated` 角色在只读事务中运行原查询的 `EXPLAIN (ANALYZE, BUFFERS)`：

| 查询 | 执行时间 | 返回行 | 被权限过滤的线索行 | 磁盘块读取 |
| --- | ---: | ---: | ---: | ---: |
| `leads` 首批 1000 条 | 6844.908 毫秒 | 0 | 3942 | 0 |
| `operational_leads` 首批 1000 条 | 6750.745 毫秒 | 0 | 3942 | 0 |

当前 `leads` 的三个 SELECT 策略会合并为 OR：线索池、受邀测评老师、历史测评老师。线索池已有直接可见分支的优化，但权限不满足时仍逐行调用 `can_view_school_lead`；其余两个分支也逐行调用带账号权限检查的函数。这个账号没有相关全局权限，最终结果为空，却仍为 3942 条线索重复执行权限判断。依赖线索可见性的来源和沟通读取放大了同一成本。

这解释了本轮约 0.9 秒出现页面外壳、约 8.8 秒才收到并显示数据的时间线。账号处于受限范围也与页面部分指标不可用相符；本轮没有逐项验证每个缺失指标的业务原因。

## 只读修复方向验证

读取并核对生产现有三个权限辅助函数后，将它们已经要求的账号权限前提放到独立子查询中，先判断是否具备进入对应逐行分支的条件。具备条件时仍调用原有表达式，继续保留归属、参与、分组、邀请和历史测评规则。

使用同一账号声明，在只读 SELECT 中显式模拟上述合并谓词，没有创建或修改生产策略。该模拟返回同样的 0 行，执行 **5.682 毫秒**，对照原 RLS 查询 6844.908 毫秒。此结果验证了本次受限账号的修复方向，**不是迁移后的真实 RLS 性能，也不是修复后的网页加载时间**。

实施时仍需把三个 SELECT 策略作为一个独立补丁，完成管理员、学服、任课／测评老师、参与／分组关系、停用及无权限账号的数据等价性验证，再按生产变更流程发布。保持现有身份与授权范围，处理查询中的重复计算。正式管理员浏览器时间仍需另测。
