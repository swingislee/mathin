# 学生名录剩余耗时：完整档案补齐与逐条权限检查

状态：**本机诊断及事务临时对照完成，两个主要瓶颈已量化；未修改应用或正式数据库函数，未发布生产。** 保持 R1-Live-2，整页 1 秒可操作尚未验收。

## 为什么之前优化后仍然慢

[最近 HAR](dashboard-local-route-har-20260921.md)中学生页面主响应为 1,543 ms，应用处理约 1,238 ms；[上一轮优化](dashboard-deep-reads-20260921.md)后，管理员名录真实 HTTP 为 997 / 1,218 / 1,413 ms。减少分组与协作投影的重复工作已有收益，但以下两条路径仍然存在：

1. [名录读取器](../../../src/features/school/student-directory-data.ts)获取完整 `studentStageRow` 后，才转换为卡片。数据库虽然先分页，当前页复杂阶段仍经 `student_record_list_rows` 逐人调用 `read_student_record_with_enrollments`，重读背景、历史来源、备注、邀请、课程和协作。一次 HTTP 并不等于数据库内部只查一次。
2. 名录调用 `student_record_index_with_enrollments`，受限角色仍逐条执行 `can_view_school_student`。此前[沟通范围优化](../../../supabase/migrations/20260920220000_communication_scope_reads.sql)将批量权限集合接入的是 `student_list_query_facts`，没有覆盖这个函数。管理员的全局可见权限会短路该分支，单测管理员首页容易遗漏它。

现有分组补丁与沟通批量读取代码都还在。这是读取路径覆盖不完整，并非已证明的旧优化被覆盖回原版。上一轮 45 组名录等价检查已留下教师 5 行仍需约 4.2–6.3 秒的样本；性能结论集中在管理员默认页，没有将教师慢路径继续收口，本次补齐该诊断缺口。

## 管理员：主要时间用于卡片不需要的完整档案

同一本地数据库、固定管理员、按班级、第一页 100 人；使用 `track_functions` 与事务内函数计数。以下取重复调用样本，时间为 SQL，不含 HTTP、Next 渲染或浏览器交互：

| 路径 | 调用次数 | 包含内部调用的耗时 |
| --- | ---: | ---: |
| 完整名录 | 1 | 850 ms |
| 当前页 `student_record_list_rows` | 1 | 624 ms |
| 其中完整档案读取 | 100 | 606 ms |
| 其中学习背景重建 | 100 | 286 ms |
| 分页前身份／阶段索引 | 1 | 166 ms |

表内父子耗时重叠，不能相加。该次还调用 `has_perm` 506 次、`is_staff` 504 次，分别约 25 / 24 ms；管理员当前主因是详情构造，不应把全部耗时归给权限。

`student_stage_learning_background` 每人重新汇集多个来源并拆解历史 `record_data.cells`，还构造负责人、老师、学习档位、班级档位、候选测评及来源 ID。卡片只用其中真实测评摘要；完整档案另外重复计算已用于分页的阶段、展开报名事实数组，并在单人读取与批量末尾两处补协作。

临时诊断函数只移除当前页详情构造，保留名录集合、分组、阶段计数、分页和顺序，耗时 **231 ms**，元数据与有序身份摘要一致。此对照只返回身份键，缺少姓名、测评和办理标记等必要字段，**231 ms 不能作为完成版页面或接口成绩**。它证明约 624 ms 的详情工作是主要优化方向。

完整 JSONB 文本约 151,812 字节；按卡片字段重组的行载荷约 35,211 字节，后者不含分页元数据。这是数据库／应用之间的数据形状对照，既不是浏览器传输了 151 KB，也不是压缩后的网络大小。

## 教师：5 行也会检查数千名学生的权限

代码默认教师使用 `scope=mine`。同样参数的首次／重复 SQL 为 **4,441 / 4,251 ms**，均返回 5 人。重复样本：

- `can_view_school_student` 调用 3,680 次，包含耗时约 **4,050 ms**；移除详情的对照仍调用 3,675 次，说明绝大多数发生在分页前的全库可见性筛选。
- 嵌套调用 `has_perm` 11,341 次、`is_staff` 15,106 次；两者自身耗时约 1,640 / 760 ms，另有逐人任课、学服及协作参与关系检查。
- 仅取消当前页详情不能解决教师慢路径；其重复样本的身份／阶段索引已占约 4,185 ms。

随后在 `pg_temp` 克隆索引及名录函数，仅将学生的逐条可见判断改为已有 `school_list_visibility(actor)` 批量集合，保留完整详情读取。相同 repeatable-read 事务中，以完整 JSONB 摘要对照：

| 账号与范围 | 原函数 SQL | 临时批量权限版本两次 SQL | 完整结果 |
| --- | ---: | ---: | --- |
| 教师“我的” | 4,346 ms | 214 / 205 ms | 5 行及所有字段、计数、顺序一致 |
| 教师“全部” | 4,234 ms | 252 / 268 ms | 5 行及所有字段、计数、顺序一致 |
| 管理员“全部” | 890 ms | 859 / 832 ms | 100 行及所有字段、计数、顺序一致 |

此对照证明现有批量权限方法适合继续用于名录；三个样本不是所有角色、筛选和历史状态的正式权限验收。临时函数随事务回滚，公共函数定义、owner 与 ACL 摘要前后一致。

## 首次波动仍需单独验证

关闭函数追踪后另开三个数据库连接，每个连接执行两次相同管理员查询：

| 新连接 | 首次 SQL | 同连接第二次 SQL |
| --- | ---: | ---: |
| 1 | 3,152 ms | 809 ms |
| 2 | 952 ms | 820 ms |
| 3 | 900 ms | 816 ms |

没有清空数据库／操作系统缓存或重启服务。这证明数据库侧本身也存在首次尖峰，但不能断言都是计划编译、磁盘冷读或 Storage。函数追踪批次首个样本为 7.14 秒，20 / 50 / 100 人后续样本约 576 / 541 / 850 ms；小页之间的全路径时间受预热与波动影响，不据此拟合每人固定开销。该批全部结果留在受控记录。

当前结论是先移除已量化的重复计算，再用同一生产构建测新进程首次、硬刷新和侧栏进入；SQL、HTTP、渲染与可操作时间分别计时。不能以暖态 SQL 或这个临时对照替代生产首屏验收。

## 下一步实现边界

1. 将名录身份读取接到查询内批量权限集合，保留原鉴权、可见／可办理差异、`mine/group/unassigned` 范围与分页语义。管理员、教师等角色分别验收实际调用量，覆盖空搜索、翻页和分组。
2. 建立当前页卡片的独立批量投影，只读姓名、年级、电话尾号、阶段、分组、真实测评摘要和办理标记。现有卡片的 `canContact` 来自 `canWrite`，测评需保留历史关联及完成判定，班级档位不能充当真实测评。
3. [选人进入沟通](../../../src/features/school/student-directory-data.ts)也使用当前完整 RPC，应保留其完整读取合同；打开档案与选人后再补背景、历史、备注、邀请等详细信息。减少首屏计算时不裁掉后续办理所需字段。
4. 名录只需要学生，而共享索引仍计算纯线索后再排除；评估学生专用候选集。剩余历史 JSON 解析参照[获客投影优化](overview-acquisition-projection-20260921.md)做批量／同步维护的小字段读取，并核对阶段和历史来源口径。

这是前几轮经验的直接延伸：分页之外还要限制每页的补齐范围；权限既要完整，也要避免对同一角色重复求值数千次。验收须同时包含管理员的宽页与教师的受限小集合。
