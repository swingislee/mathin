# 大屏笔迹输入与绘制分析 · 2026-09-12

状态：生产只读聚合与本地算法复算完成。起笔等待、平滑拖尾及掌擦绘制口径已有代码依据；实际大屏输入到显示的耗时尚未测量。本轮修正分析报告，应用和生产保持原版本，不登记为交互已修复或人工验收通过。

## 现场依据与分析范围

- 大屏直接打开 `mathin.club`；用户明确“空白页第一笔就明显”，进一步补充每一笔都落在书写后面、慢写会好一些，设备为 Windows 上的 Chrome / Edge。因此累计笔迹负担的优先级降低，先查输入到首笔显色和笔尖跟随。
- 老师到下课时间没有点击“下课”；本次不把缺少结束事件归因为保存故障，也不将课后问题排在书写体验之前。
- 沿用[正式课堂只读核查](classroom-formal-session-analysis-20260912.md)定位的同一上午课次，补充查询使用 `BEGIN READ ONLY`、8 秒 statement timeout、`ROLLBACK`；确认 transaction_read_only=on，只返回汇总，不导出原始笔迹、身份、学生信息。
- `CanvasSurface`、`strokes`、`BoardInputSink`、输入 router、掌擦手势及依赖 lockfile 与已登记生产候选 `aed8fec4` 比较一致。复算调用本地安装的 `perfect-freehand@1.2.3`，使用合成输入，未控制大屏或浏览器。

## 1. 起笔反馈要等移动和下一绘制帧

`CanvasSurface.tsx:315` 的 beginGesture 只建立 stroke 和广播开始消息，没有绘制初始点。`BoardInputSink.begin` 也只记录起点，直到 push 收到移动后才请求 animation frame。以真实 BoardInputSink 加可控调度器复算：

| 阶段 | 已输出绘制批次 | 已请求帧 |
| --- | --- | --- |
| pointerdown | 0 | 0 |
| 第一次 move 后、帧回调前 | 0 | 1 |
| 下一帧回调 | 1 | 1 |

因此停留在落笔位置时，当前笔画本身不会立即反馈；单点通常到松手提交时才出现。后续仍有 0.75 CSS px 的轻量重采样。帧合批是正常的调度选择，但起点完全依赖后续移动可以独立改进。实际等待包含触点移动、事件投递、帧排队和显示过程，不能把它写成固定 16.7ms。

Smart 在可点击控件上额外等待 8 CSS px 才接管为笔迹；纯书写区域直接进入 inking。这个阈值是条件路径，不能笼统解释所有空白页延迟。

## 2. 当前算法明确让笔迹末端落后于输入点

`strokes.ts:36` 对预览和最终笔画都使用 `thinning=0.7 / smoothing=0.6 / streamline=0.5`，没有传 `last`。安装包源码的 `getStrokePoints` 实际默认 `last=false`，以插值调整中心线；本地复算与该源码一致。上游[选项说明](https://github.com/steveruizok/perfect-freehand#options)也说明 `last=true` 会把末端放到最后输入点；网页表格的默认值与安装包实现不同，本次以锁定版本实际代码为准。

合成水平线 40 个点、size=6，比较中心线最后一点与输入末点的距离：

| 每次输入前进 | 当前配置末端落后 | 显式 last=true | streamline=0 |
| --- | --- | --- | --- |
| 2 CSS px | 1.4783 px | 0 px | 0 px |
| 5 CSS px | 3.6957 px | 0 px | 0 px |
| 10 CSS px | 7.3913 px | 0 px | 0 px |
| 20 CSS px | 14.7826 px | 0 px | 0 px |

这是几何位置差，不是性能计时，也不是教师现场测量。它说明即使计算立即完成，中心线仍可跟在输入点后面；触点移动越快、相邻点越远，视觉追赶越明显。最终重放也没有标记完整笔画，原始终点被保留不等于渲染终点对齐。

优先方向是让实时笔尖更贴近最新输入，并在收笔时明确处理完整笔画。预览与持久重放应使用可解释、相容的几何规则，避免松手后整条线改变形状。不能只全局修改 last 或平滑系数就登记视觉问题已解决。

## 3. 掌擦还有启动和擦除范围两层差异

`useClassroomViewportGestures.ts:123` 识别手掌后先保留手势，到下一次 move 才 begin/append；Canvas 随后仍按帧处理。掌擦游标通过 React state 更新，当前掌擦路径每次只传该事件最新点，没有复用画笔的 coalesced 点批次。

`CanvasSurface.tsx:309` 为每段擦除调用同一个 drawItem，因而擦除也经过平滑和模拟压力。以当前参数、标称直径 100 px 的两点水平擦除复算，移动 2/10/40 px 时，生成轮廓高度分别约 65.49/67.29/71.76 px，中心线末端分别落后 0.85/4.25/17 px。这说明圆形游标的直径与实际擦除轮廓没有一致的几何保证；数值来自合成输入，不是实际手掌测量。

同时，工具栏的 lastEraser 是组件本地状态；掌擦端口只传 eraserWidth，固定构造局部 erase，无法遵循所选整线橡皮。这项行为差异已确认。

下一增量应让掌擦读取共享橡皮模式、识别后及时反馈，并为局部擦提供与游标一致的扫掠范围。局部擦逐帧反馈与最终重放须一致，整线擦则复用命中、撤销和同步语义。不能只换成恒定宽度笔刷而改变历史 erase 的重放外观。

## 建议的最小下一增量与验收

1. 优先改善初始落点显示及实时笔尖跟随，补齐收笔终点处理；保留现有尾部增量绘制，不按整堂笔迹总量另起全量渲染改造。
2. 同批处理掌擦默认模式、开始反馈与局部擦范围一致性；取消、撤销、最终重放及主副板书作为定向合同。
3. 在同一实际大屏人工比较空白页点按、慢写/快写、抬笔终点及两种橡皮模式；再在较多笔迹页比较，确认优化没有引入累积负担。
4. 如需量化，仅采集事件投递等待、首笔绘制提交、帧间隔、绘制 CPU 耗时、输入类型及取消原因的统计；显示延迟还需要设备侧观测。现有服务端数据无法补出这些指标。

本轮检查为只读 SQL 汇总、锁定版本源码比较与确定性合成输入复算；没有运行全量回归，没有以本机结果替代实际大屏验收。

## 继续排查：每笔拖后、慢写较好

慢写好转同时符合两类机制：固定时间的输入/帧/显示等待，会在移动更快时形成更大的空间距离；当前平滑算法也会随相邻输入距离增加而产生更大中心线拖尾。现场描述增强了这条排查方向，但不能仅靠它确定各部分延迟占比。

### 4. 模拟压力让快写更细，放大可见间距

画笔没有传真实压力，perfect-freehand 默认用点距模拟压力，thinning=0.7 再把它转为可变线宽。同样标称 12 px、40 点水平线，仅改变相邻点间距：

| 点间距 | 整条输出轮廓高度 | 输入末点与最右轮廓的关系 |
| --- | --- | --- |
| 5 px | 13.35 px | 轮廓比末点向右伸出 2.97 px |
| 10 px | 6.66 px | 轮廓落后末点 4.20 px |
| 20 px | 4.71 px | 轮廓落后末点 12.99 px |

该复算不等同于设备速度或压力测量，但证明：在采样间隔近似固定时，快写导致点距增加，不仅中心线拖尾增大，线条还可能变细，较厚端帽对拖尾的遮盖随之减小。因此“慢写更好”不只是耗时问题，还与笔迹几何外观有关。采样密度也会改变这个效果。下一增量应明确教学书写是否需要这类模拟粗细，保持所选笔宽的可预测反馈。

### 5. 预览尾段与收笔全量生成的轮廓不同

`CanvasSurface.drawLocalDraftTail` 每次取新点及之前 12 点，重新运行无状态的 getStroke，并把结果直接叠加到 draft，既不清除旧尾部，也不继承前段平滑/压力状态；收笔则在 base 上对完整笔画重新计算。因此预览并不是最终轮廓的简单增量。

按实际尾段算法复算一条 50 点正弦曲线（x=30+3i，y=65+25sin(i/5)，size=12），用 1 px 网格及 Canvas 默认 nonzero 填充规则比较预览多边形并集和最终多边形：每批 1/3/6 点时，预览额外区域占最终面积约 1.44%/0.91%/0.91%，最终有而预览没有的采样格分别为 205/192/169，最终面积为 2,854 格。此为几何采样近似，不含抗锯齿和 GPU 显示。

该差异可导致书写中的轮廓在松手后变化，尤其转弯和端部。它是已复现的显示一致性问题，尚不能量化为教师感受到的延迟。优化时应保证尾段替换、压力/平滑状态及最终收笔一致，避免用一层层旧轮廓覆盖来更新笔尖。

### 6. 实际输入热路径存在重复几何读取和路径构造

通过仓库已有 jsdom、真实 React/CanvasSurface 和记录调用的 Canvas 替身，向 ink-lock 路径发送一次包含 8 个 coalesced 样本的 move：

- `getBoundingClientRect` 调用 10 次：move 自身一次、8 个样本各一次、事件当前点一次。
- 本帧再读取 computed style 一次，并构造一个 SVG 路径字符串及 Path2D。
- 普通笔迹点保存在 ref 中，批次直接绘制；并非每个点都触发整棵课堂 React 树重绘。

调用次数已复现，实际 CPU 和布局耗时待设备测量。矩形可以在同一事件批次复用，颜色可以在主题/颜色改变时更新；再按测量决定是否改用直接路径构造。按帧提交本身还会等待刷新时机，[requestAnimationFrame 文档](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)说明它安排下一次重绘前的回调；这不能被表述为现场固定增加某个毫秒数。

### 7. 连续提交被合并时，画布只处理最后一项

在上述 DOM 模拟环境挂载真实 CanvasSurface，使用实际 store 连续 commit 两条笔迹，再允许 React 更新：store 保存 2 条，base 只执行 1 次 fill，renderMutation.items 只剩最后一条。若两次提交之间允许 React 分别更新，store 和 base 均为 2 条/次。

原因是 store 每次 commit 用当前一项覆盖 renderMutation，Canvas 的 effect 只消费最后一次 append；中间项没有补画。该复现覆盖同一批渲染之前的突发提交，可导致已保存内容暂时未显示；它不证明老师本节课发生了漏笔，也不足以解释每笔持续拖后。修复应按未绘制的版本/条目补齐，并覆盖混合追加、清除、撤销，保持持久数据与显示一致。

### 8. 核对实际路径后，降低其他假设优先级

正式冻结页共 31 页，全部为 source-runtime-page-v1，全部有 H5 绑定；其中 advanceOnCanvasClick 为 true 的 4 页、false 的 27 页。但开课时已生效的生产开关是 classroom_input_v2=true、classroom_h5_pointer_v1=false。根据页面 props、bridge 状态和 renderer profile，正常主板书画笔走直接 ink-lock 路径。

因此 H5 shim 的帧合批 → postMessage → Canvas 第二次帧合批，以及 Smart 点击区域 8 px 接管门槛，是代码中存在的条件路径，当前证据不支持把它们计入本节课主板书延迟。H5 bridge 将来启用时再单独验收这条路径。快照准备已放入 Worker，也不在每个移动样本上执行。

Windows Chrome / Edge 的合成与显示等待仍是未测量因素。当前使用默认 2D context；Chromium 提供可尝试的 [desynchronized 低延迟提示](https://developer.chrome.com/blog/desynchronized)，但支持情况、透明双层画布的收益以及闪烁/同步代价需要在实际设备核实，不能通过添加一个参数便宣称问题已解决。

下一次定向测量同时记录：事件投递等待、coalesced 样本数量、帧间隔、绘制提交耗时、pointerType、画布有效 DPR 和 context attributes。先优化已复现的起笔、拖尾、轮廓一致性及提交补画，再判断硬件加速、刷新率和显示合成是否仍占主要时间。所有本地复算均未修改业务代码或生产。
