# 大屏笔迹输入与绘制分析 · 2026-09-12

状态：生产只读聚合与本地算法复算完成。起笔等待、平滑拖尾及掌擦绘制口径已有代码依据；实际大屏输入到显示的耗时尚未测量。本轮修正分析报告，应用和生产保持原版本，不登记为交互已修复或人工验收通过。

## 现场依据与分析范围

- 大屏直接打开 `mathin.club`；用户明确“空白页第一笔就明显”。因此累计笔迹负担的优先级降低，先查输入到首笔显色和笔尖跟随。
- 老师到下课时间没有点击“下课”；本次不把缺少结束事件归因为保存故障，也不将课后问题排在书写体验之前。
- 沿用[正式课堂只读核查](classroom-formal-session-analysis-20260912.md)定位的同一上午课次，补充查询使用 `BEGIN READ ONLY`、8 秒 statement timeout、`ROLLBACK`；确认 transaction_read_only=on，只返回汇总，不导出原始笔迹、身份、学生信息。
- `CanvasSurface`、`strokes`、`BoardInputSink`、输入 router、掌擦手势及依赖 lockfile 与已登记生产候选 `aed8fec4` 比较一致。复算调用本地安装的 `perfect-freehand@1.2.3`，使用合成输入，未控制大屏或浏览器。

## 1. 起笔反馈要等移动和下一绘制帧

`CanvasSurface.tsx:315` 的 beginGesture 只建立 stroke 和广播开始消息，没有绘制初始点。`BoardInputSink.begin` 也只记录起点，直到 push 收到移动后才请求 animation frame。以真实 BoardInputSink 加可控调度器复算：

| 阶段 | 已输出绘制批次 | 已请求帧 |
| --- | --- | --- |
| pointerdown | 0 | 0 |
| 第一次 move 后、帧回调前 | 0 | 1 |
| 下一帧回调 | 1 | 1 |

因此停留在落笔位置时，当前笔画本身不会立即反馈；单点通常到松手提交时才出现。后续仍有 0.75 CSS px 的轻量重采样。帧合批是正常的调度选择，但起点完全依赖后续移动可以独立改进。实际等待包含触点移动、事件投递、帧排队和显示过程，不能把它写成固定 16.7ms。

Smart 在可点击控件上额外等待 8 CSS px 才接管为笔迹；纯书写区域直接进入 inking。这个阈值是条件路径，不能笼统解释所有空白页延迟。

## 2. 当前算法明确让笔迹末端落后于输入点

`strokes.ts:36` 对预览和最终笔画都使用 `thinning=0.7 / smoothing=0.6 / streamline=0.5`，没有传 `last`。安装包源码的 `getStrokePoints` 实际默认 `last=false`，以插值调整中心线；本地复算与该源码一致。上游[选项说明](https://github.com/steveruizok/perfect-freehand#options)也说明 `last=true` 会把末端放到最后输入点；网页表格的默认值与安装包实现不同，本次以锁定版本实际代码为准。

合成水平线 40 个点、size=6，比较中心线最后一点与输入末点的距离：

| 每次输入前进 | 当前配置末端落后 | 显式 last=true | streamline=0 |
| --- | --- | --- | --- |
| 2 CSS px | 1.4783 px | 0 px | 0 px |
| 5 CSS px | 3.6957 px | 0 px | 0 px |
| 10 CSS px | 7.3913 px | 0 px | 0 px |
| 20 CSS px | 14.7826 px | 0 px | 0 px |

这是几何位置差，不是性能计时，也不是教师现场测量。它说明即使计算立即完成，中心线仍可跟在输入点后面；触点移动越快、相邻点越远，视觉追赶越明显。最终重放也没有标记完整笔画，原始终点被保留不等于渲染终点对齐。

优先方向是让实时笔尖更贴近最新输入，并在收笔时明确处理完整笔画。预览与持久重放应使用可解释、相容的几何规则，避免松手后整条线改变形状。不能只全局修改 last 或平滑系数就登记视觉问题已解决。

## 3. 掌擦还有启动和擦除范围两层差异

`useClassroomViewportGestures.ts:123` 识别手掌后先保留手势，到下一次 move 才 begin/append；Canvas 随后仍按帧处理。掌擦游标通过 React state 更新，当前掌擦路径每次只传该事件最新点，没有复用画笔的 coalesced 点批次。

`CanvasSurface.tsx:309` 为每段擦除调用同一个 drawItem，因而擦除也经过平滑和模拟压力。以当前参数、标称直径 100 px 的两点水平擦除复算，移动 2/10/40 px 时，生成轮廓高度分别约 65.49/67.29/71.76 px，中心线末端分别落后 0.85/4.25/17 px。这说明圆形游标的直径与实际擦除轮廓没有一致的几何保证；数值来自合成输入，不是实际手掌测量。

同时，工具栏的 lastEraser 是组件本地状态；掌擦端口只传 eraserWidth，固定构造局部 erase，无法遵循所选整线橡皮。这项行为差异已确认。

下一增量应让掌擦读取共享橡皮模式、识别后及时反馈，并为局部擦提供与游标一致的扫掠范围。局部擦逐帧反馈与最终重放须一致，整线擦则复用命中、撤销和同步语义。不能只换成恒定宽度笔刷而改变历史 erase 的重放外观。

## 建议的最小下一增量与验收

1. 优先改善初始落点显示及实时笔尖跟随，补齐收笔终点处理；保留现有尾部增量绘制，不按整堂笔迹总量另起全量渲染改造。
2. 同批处理掌擦默认模式、开始反馈与局部擦范围一致性；取消、撤销、最终重放及主副板书作为定向合同。
3. 在同一实际大屏人工比较空白页点按、慢写/快写、抬笔终点及两种橡皮模式；再在较多笔迹页比较，确认优化没有引入累积负担。
4. 如需量化，仅采集事件投递等待、首笔绘制提交、帧间隔、绘制 CPU 耗时、输入类型及取消原因的统计；显示延迟还需要设备侧观测。现有服务端数据无法补出这些指标。

本轮检查为只读 SQL 汇总、锁定版本源码比较与确定性合成输入复算；没有运行全量回归，没有以本机结果替代实际大屏验收。
