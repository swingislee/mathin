# Dashboard HAR 热点与底层读取复查

状态：**两条查询迁移已应用本机开发库，课件页读取并行化已接入；机器检查通过，待人工体验验收。生产未发布，整页 1 秒目标未达成验收。** 保持 R1-Live-2，不关闭 Gate。

## 为什么前几轮仍有慢点

对照[最近本地 HAR](dashboard-local-route-har-20260921.md)、[9 月 19 日查询优化](dashboard-query-audit-20260919.md)、[表格数据库分页](table-database-pages-20260921.md)及[总览统计内核](overview-aggregate-core-20260921.md)：

- 本地账本中学生名录、名录分组排序、素材查询、课件进度汇总及总览 `07000/08000` 共六条迁移均已存在，规范化校验和与仓库一致。本次热点中没有发现旧函数被后续迁移覆盖回原版的证据。
- 课件进度已经改为汇总，但任务队列是另一条 RPC。它仍先计算所有讲次的页数、草稿和最后编辑，再取第一页；旧计划扫描约 16.4 万条修订、排序约 16 万行并写入临时文件。
- 素材已做数据库分页，但“引用数排序”仍先计算所有素材的引用数、课程数、讲次数。原版轨道扫描约 27.6 万条引用，宽表读取约 1.29 万个块，去重排序写临时文件。返回 11 行不能证明底层只处理 11 行。
- 学生名录已有权限、筛选、排序和分页；分组阶段仍无条件给全部约 3,675 个身份计算协作展示信息，并为每个身份重复扫描分组集合。分页后的复杂阶段仍逐人读取完整档案，属于尚存开销。
- 新总览聚合读取器仍只是获客、沟通两项的内核，完整页面尚未接入。已有两项优化不能直接替代此前记录的完整总览约 8.79 MB 读取；后续仍须完成其他指标与明细边界后统一接入。

最新 HAR 为开发构建的站内切换样本，未包含 document / 硬刷新计时。课程页 9.04 秒主要在框架准备，而课件、素材、学生的耗时主要在应用读取；不能用同一原因解释全部路由。素材浏览器图片在主响应尾部才发起，也不能将这些图片请求当作此前数据库等待的原因。

## 本轮改动

`20260921009000_dashboard_courseware_narrow_reads`：

- 任务队列先按权限、轨道、搜索和标签确定本页讲次，随后补页数、草稿、发布号和编辑人。最后修订按页面索引取一条，再取讲次的最后一条，避开修订正文扫描和全量落盘排序。
- “最近编辑”仍须检查候选讲次的最后编辑时间，但改为逐讲次取最后值；“待发布”使用仅含草稿的索引。
- 保留原排序键；相同排序值最后增加课程、讲次 ID。旧“待发布”有 6 个位置因并列值而不稳定，完整记录集合与字段一致；等价对照的旧算法也仅补这两个最终排序键。
- 素材的引用次数继续在分页前计算；课程数、讲次数只补当前页。原版和适配轨道分别使用窄部分覆盖索引，避免把重复轨道文字存进索引键；补充未删除页面和最后修订的覆盖索引。
- 素材 RPC 的 `work_mem` 限定为 16 MB，避免当前约 6.6 万个引用分组在默认 4 MB 下落盘。仅影响该函数的工作内存，增加索引也会带来写入维护成本；没有调整全库设置。
- 课件页的任务、进度和预览独立读取并行启动，队列组件使用已加载任务，消除先等进度再发任务查询的串行链。

`20260921010000_student_directory_group_reads`：

- 仅负责人／协作组分组需要所有身份的协作投影；其他分组由当前页详情补齐协作字段和办理权限。可见范围判断仍在分页前执行。
- 分组集合一次去重、按身份聚合，保留未分组兜底、排序、总数、阶段计数、选择顺序及联系入口。
- 不改变 RPC 参数、返回结构、owner、执行权限和既有 RLS；不以减少每页人数或丢弃历史记录换取速度。

## 仍须继续处理的明确边界

1. 学生名录当前页仍补全档案、历史来源、邀请、备注和协作，再裁剪为卡片；部分行在单条读取及批量末尾重复补协作。应建立卡片所需字段的独立批量投影，同时保留选人沟通所需完整读取，做字段和角色等价对照。
2. 素材排序仍读取全部引用计数，最近编辑仍检查全部候选讲次。数据继续增长时应评估事务维护的引用计数／讲次编辑摘要，而不是再次扩大查询缓存掩盖扫描。
3. 完整总览 C+D 接入、课表与五个工作区水合后的晚发／重复请求、课件无预览时仍可达的重型客户端依赖，仍在上一份 HAR 的待办范围。本批没有宣称这些问题已关闭。
4. 完整页面须在生产构建下分别复测新进程首次、硬刷新、侧栏切换，并使用数据可操作标记；当前接口或 SQL 提速不等于整页 1 秒目标已实现。
