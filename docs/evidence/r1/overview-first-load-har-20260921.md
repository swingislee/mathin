## 确认的查询瓶颈

以生产现有活跃管理员的 authenticated 权限上下文执行只读 SQL，保留实际 RLS。只回传执行计划摘要、计数及哈希，业务 JSON 和分页游标留在生产进程内。

近期[获客来源增量修复](overview-acquisition-incremental-production-20260921.md)新建的 RPC，在输出每条记录时，使用相关子查询从 `versions` CTE 重新收集该来源的所有历史别名。生产有 4125 个版本、3861 条最新来源，前端每页最多 1000 条，串行读取四页。

- 第一页真实 RPC：799.48 ms；展开函数体后为 794.21 ms。
- 第一次执行计划中，版本集合扫描约 193.56 ms；别名子查询执行 1000 次，每次扫描 4125 行并过滤掉约 4124 行，合计约 443 ms。
- 完整四页的 SQL 执行约 **3083.14 ms**；结果 JSON 文本约 2.44 MB，仅统计字节数，没有导出业务正文。
- 同权限下，线索首批约 3.85 ms、沟通首批 63.47 ms、活动 31.10 ms、测评结果 11.29 ms、当前运营线索 105.70 ms。已有权限优化仍在生效。

这是新查询中的重复全量扫描开销，并非旧权限补丁丢失。它在每次查询都会发生，重复刷新也会付出成本。上述 SQL 计时与 HAR 使用同一生产版本，但不是同一次请求的分段追踪；不能把原 HAR 的全部 5.26 秒精确归因给这一条 RPC。
