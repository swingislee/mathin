# 统一档案与联系工作安排

> 状态（2026-09-08）：统一档案与再联系工作单已交付开发端，待人工视觉与业务验收。本批不改变生产或 R1-Live Gate。

学生工作区通过“本轮工作／全部档案”切换范围。姓名、电话搜索进入全部档案，并保留负责范围与列筛选。完整沟通、测评和报名经历按原有身份读取；原来的历史核对入口转向全部档案。来源日期用于解释经历，具体疑点继续在个人资料中核对。

本轮名单保留既有范围；阶段按完整事实表达，在读和有效课程仍采用当前业务关系。课程结束或停读单独表达。老师可以直接登记本次联系，原始凭据、旧记录、身份和报名状态保持连续，不要求先恢复或逐条确认导入。

为保持全范围列筛选与分页，同时控制读取耗时，服务端一次读取列表摘要，浏览器接收最终一页。已有邀约保留完整 ID、版本与初始内容，登记继续更新同一事项；专业上下文按打开的学生读取。

“再联系建议”提供曾未接通、已有测评、曾就读和联系记录较少四组。建议避让当前在读、本轮已有安排、近 7 天联系、失效号码及明确勿扰备注；同号码在本轮建议中出现一次，保留各自学生及线索身份。来源记录使用实际发生日期，未知日期继续留空。

选定联系人后填写本轮目的、负责人和日期，创建既有沟通工作单。页面提供“选择前20位”便于小批试行，实际人数由老师选择，单批最多 100 位。工作单保存成员顺序，支持逐项完成和跨天继续；计划日期到达后进入相应负责人的日期工作台。安排只记录本轮工作，实际联系结果由办理时登记；未选资料保持可检索。

## 开发验证与应用

`scripts/unified-student-records.mjs` 每次核对本机主机、实际 Supabase origin、监听进程、Docker 网络与数据库指纹；只支持已登记的隔离开发目标。

依次对默认模式、`--projection`、`--entry-context` 执行 `--preflight`、`--check`、`--apply`，分别对应迁移 `20260908008000_unified_student_records`、`20260908008100_student_record_list_projection`、`20260908008200_student_record_entry_context`。检查使用固定开发身份，合成业务夹具全部回滚；应用要求相同代码与数据库版本的检查结果，并比较业务表内容指纹。

再联系增量使用同一脚本的 `--recontact` 模式，对应 `20260908009000_student_recontact_worklists`，沿用相同的目标核对、检查与应用流程。已有工作单的 `is_scheduled` 默认值为 false，保留原有名单快照的行为；新安排通过专用入口创建。负责人变化复用既有分配权限，提交时重新核对归属与建议资格，相同请求可安全重试。

已验证范围：名单外客户可查、可继续沟通，原记录保留，读取不创建任务，重复请求不增加联系次数，其他负责人及非员工权限拒绝，全范围摘要与分页字段一致，已有邀约上下文完整。中英文开发页面 HTTP 200，服务器渲染无错误；全部档案列表本轮观测约 1.4 秒出现。机器结果不代替人工验收。

本批运行的学生列表、字段分页、登记交互、工作单动作与工作日读取定向测试通过。再联系数据库检查覆盖同号码去重、勿扰避让、归属冲突、幂等重试、未来日期、完成后退出、分配给固定教师后继续办理、其他负责人及非员工拒绝；夹具回滚后业务内容指纹一致。全仓类型检查还报告其他任务涉及的 `autumn-identity-review`、`source-reconciliation` 测试类型错误；本任务变更未出现类型错误，未据此宣称全仓类型检查通过。
