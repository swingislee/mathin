# 更新源表交叉整理

当前批次以 `2026-09-07【思维】用户与产品运营表.base` 为业务主来源。魔法校的学生、班级、花名册和场地导出用于身份与目录比对；`员工管理.xlsx` 与产品负责人补充确认共同确定现有员工范围。其他 `.base`、子2工作簿与既有小地推导出提供历年报名、授课、获客和沟通的交叉依据。

本流程交付来源匹配预览。源表重算读取原文件，在私有目录封存副本并生成结果；秋季主档核对再读取已确认的本机开发库快照。后续业务批次沿用 [业务历史记录规则](business-record-history-state.md)，按目标库重新核对已有身份、来源映射和人工修订。

## 执行

入口为 `scripts/source-reconciliation.mjs`，匹配合同在 `scripts/lib/source-reconciliation.mjs`。

```powershell
node scripts/source-reconciliation.mjs --run .tmp/source-refresh/run-<新批次> --python <依赖运行时Python绝对路径>
```

`--source` 默认为 `docs/test_material`。`--previous-base` 可指定上一版封存的 `.base`；`--decisions` 可指定私有、带确认依据的员工别名 JSON；`--staff-review` 接收 `staff_review_confirmation_ledger`，其中 `confirmedBy` 与每条决定的 `sourceName`、`decision`、`evidence` 必填。原始文件按相对路径封存，manifest 保存字节数和摘要。结果位于新建的 `analysis-<时间>/reconciliation.json`，批次内的 `latest-analysis.json` 指向最近结果。`--reuse` 复用同批次提取文件，仍核对原文件集合与原文件、封存副本的全部摘要。输入有变化时创建新批次。

本次 `.base` 与配套导出的文件名属于已验证输入合同。后续更换权威批次时，先核对文件与字段合同，再升级配方。原版本继续保留。

## 匹配规则

- 当前业务状态取飞书业务字段及其所属时期。秋季在读、待报名和未填写分别保留；魔法校的历史状态、无年级或旧班级状态只形成对照差异。
- 员工按当前名单分类。学科、学段、序号和待定占位名称排除真实员工导入。名单外的完整老师姓名作为历史署名；简称、渠道、活动与状态标签分别保留待核对。历史署名不生成当前员工账号。
- 人工补充当前员工时保留空的魔法校员工 ID，以规范姓名身份关联各处署名。姓名更正及别名沿用目标的当前或历史归属；兼职称呼单列，实名与当前任职状态分别留待补充。暂不确定的登记保持待核对。决定冲突、占位目标及别名环路会停止匹配。
- 同一名单姓名明确包含的中英文别名可唯一关联。`--decisions` 沿用 `name`、`employeeId`、`confirmedBy`、`evidence` 格式；`--staff-review` 的姓名更正与别名使用 `canonicalName` 指定规范姓名，保留确认人与依据。占位目标和冲突别名拒绝关联。真实姓名与占位式联系方式分开处理。
- 魔法校学生 ID 是参考身份键。姓名与全部完整电话共同命中唯一 ID 时关联；同名、仅家庭电话、矛盾电话和重复候选保持待核对。姓名中的备注或疑似错别字保留原样。
- 秋季主表没有电话时，可使用完整姓名与当期班级花名册共同定位。班级须同时符合 2026 秋季、年级、校区、班型、老师、周次与时段。旧年度仍标为开课中的班级不用于此规则。
- 完整姓名与相同完整电话集合形成全来源联系组。多个来源位置仍保留各自业务事实；同一电话下的不同姓名保持独立。秋季表中的同名联系组仅提供候选电话，不自动认领身份。
- 横向名单逐姓名单元格拆分，保留所属班级块与原位置。记录数、姓名位置数和独立人数分别统计。
- 班级文件名中的来源 ID 用于关联花名册。空班文件即使字节完全相同，也按各自相对路径保留。班级汇总与明细逐行按多重集合对照，业务关联使用明细，避免把两份导出相加。
- 场地使用校区与教室名称组合定位。来源中的占位目录、占位教室和未填写教室单列核对；校区目录不生成组织、权限或班级作用域。
- 飞书修订按表 ID、记录 ID、字段 ID 对照。显示值更新与原始导出表示变化分别记录；本次未出现的旧记录继续保留在旧快照中。
- 主业务 `.base` 按明确文件名选择。其他 `.base` 只补充历史依据，其来源键含文件名，当前主表计数与状态保持独立。

## 秋季学生主档与班级核对

入口为 `scripts/autumn-identity-review.mjs`，身份合同在 `scripts/lib/autumn-identity-review.mjs`。

```powershell
node scripts/autumn-identity-review.mjs --run .tmp/source-refresh/<核对批次> --source-run .tmp/source-refresh/<来源批次> --capture
node scripts/autumn-identity-review.mjs --run .tmp/source-refresh/<核对批次> --source-run .tmp/source-refresh/<来源批次>
```

`--capture` 复用本机目标核对，在一个 `REPEATABLE READ READ ONLY` 事务内读取学生、线索、联系方式、已完成导入映射、班级花名册、已有业务归属及修订状态。快照只含本次所需字段，不导出绑定码或班级邀请码。普通模式核对快照与来源结果摘要，再生成独立核对结果；两种模式均无数据库写入。

- 来源身份已定位时，通过已完成的魔法校导入映射或同一飞书记录的既有归属定位开发库主档。姓名变化、删除状态、多个归属保持待核对。
- 同名来源中的电话、家庭共用电话和已有线索提供候选。没有找到候选时仍只提出新建候选，明确需要补充或确认的姓名与联系方式。
- 班级分别核对秋季排课组合、魔法校目录和开发库已有班级；记录数与独立学生数分开。已有主档、业务条目及人工修订保留原值，当前业务状态取主表。
- 工作簿的确认栏仅记录人工决定。实际关联、新建、年级更新和业务导入沿用后续批次的目标核对与写入合同。

2026-09-07 本机只读核对了 1,522 条学生主档与 1,074 条线索。秋季 166 条记录中，47 条可关联已有主档、112 条待确认身份、6 条新建候选、1 条来源待补。47 条可关联记录对应 47 个不同主档，其中 45 条原主档年级未填、1 条已填年级与秋季表不同；38 条已有对应班级的有效花名册记录。28 组排课信息中，15 组可关联已有班级、11 组待核对、2 组信息待补。本轮业务写入为 0。

私有工作簿包含学生核对、班级核对、候选依据、员工确认四页，共 166 条秋季记录、28 组排课信息、589 条候选来源位置与 14 条员工确认。按学生编号筛选依据，在黄色栏选择核对决定并填写确认对象或更正信息。

## 一线资料确认开发入口（2026-09-07）

产品负责人不直接接触一线，学生事实由任课老师、学服在日常工作中逐步补齐。开发入口为 `/zh/dashboard/students/confirm`（同时支持 `/en`），可从学生名单的“秋季资料确认”进入。

- 本批将 166 条秋季来源记录和 28 组排课信息保存为独立底稿。底稿保留来源摘要和原值；学生、家庭、正式班级与报名保持原值。
- 管理员按名单中的老师及上课信息安排负责同事，任课老师和学服分别分配。待安排的底稿由管理员查看；一线只读取和反馈明确分配给自己的班级。当前已载入底稿，实际负责同事尚待安排，不按姓名自动赋予权限。
- 任课老师确认姓名、年级、排课和在读情况；学服在需要身份补充的记录中增加家庭联系方式。其他来源的候选电话、来源 ID、身份合并选择和技术匹配状态留在整理环节。
- 每项可选“情况一致”“补充情况”“暂时不清楚”。空白事实提供补充或暂缓选项。可以只确认一项，暂不清楚时无需填写理由；普通保存停留当前学生，保存并下一位仅在成功后前进。
- 草稿在当前页面内按学生及分工保存，切换学生可继续填写。页面刷新前应先保存反馈。任课与学服反馈各自保留提交人、时间和修订；并发变化先展示最新反馈，由填写人决定如何继续。
- “已反馈”“已确认部分”“下次再了解”描述反馈状态。身份关联、新建、字段覆盖和报名变更继续按后续整理批次处理，不由一线点击确认自动触发。

实现使用 `student_profile_review_batches/groups/items/responses/events`，RPC 分别承载分配和事实反馈；原始候选资料继续保存在私有来源目录。所有表开启 RLS，受分配关系、当前员工状态和任课／学服范围约束，事件审计由管理员读取。页面与 Action 仅在开发环境和已登记的本机 Supabase origin 开放。

本机执行入口：

```powershell
node scripts/student-profile-review.mjs --preflight
node scripts/student-profile-review.mjs --check
node scripts/student-profile-review.mjs --apply
```

`--preflight` 核对主机、实际 origin、监听进程、Docker 网络与数据库指纹。`--check` 在同一事务内执行 schema、底稿导入、固定账号 RLS／反馈／并发／撤销分配断言并回滚；`--apply` 核对相同 migration、来源和断言摘要后写入独立底稿，检查学生和报名原值摘要、Auth 账号数量保持不变。重复导入复用稳定来源键，不覆盖原始记录、负责安排或反馈。
