## 交付边界

按[读取升级设计](../../plan/dashboard-statistics-read-model-upgrade.md)先实现 A 的数据基线与 B 的获客/沟通聚合。产品负责人将主要数据可操作目标收紧为 **首次打开、硬刷新和侧栏进入均在 1 秒内**；SQL、完整数据读取预算分别调整为 100/250 毫秒，均作为后续完整路径的目标。

新增读取器尚未接入总览页面。现有页面继续使用原读取器；原算法与两项新汇总仅在隔离验证时对照。其他四项业务指标、教师结果、容量、目录/月目标、工作角标和按页明细仍属于 C+D。当前不能据两项统计内核的耗时宣称整页达标。

## 实现

- `20260921007000_overview_acquisition_contact_aggregation` 为历史获客、沟通和活动报名增加确定性的 STORED 统计字段。生成表达式读取原始字段，写入与更新在同一事务内维护；原文仍保留。
- 获客保留来源最新版本、旧别名、主来源优先、首次提交补充及原生 Lead 日期；沟通保留月/周差异、来源版本去重、followup 排除、补充确认去重和来源署名。确认月份分别表达缺失、显式 null 与有效月份，缺日期数量继续独立汇总。
- `get_staff_overview_acquisition_contacts_v2` 在数据库内计算两项计数、日趋势和人员归属。返回 schemaVersion=2 的汇总，不返回原文、电话、证据和历史别名数组。类型校验失败或 RPC 不可用会显式报错。
- 来源权威判定复用原来的条件和维护角色，批量核对本次授权候选中的来源 ID。批量函数只返回输入中通过判定的 ID；业务记录仍使用调用者 RLS，原生记录的空来源继续保留。迁移核对原函数和 business view 条件，发现漂移即停止。
- 批量查询使用固定 SQL 与绑定参数，按实际来源数量规划，避免数千个 ID 沿少量参数的通用计划反复点查。该做法依据 [PostgreSQL 15 的 EXECUTE 参数规划说明](https://www.postgresql.org/docs/15/plpgsql-statements.html#PLPGSQL-STATEMENTS-EXECUTING-DYN)。
- 获客异常 text 保留原文及错误标记，统计读取显式失败，避免将数字或数组转换成有效业务文字。生成函数 owner 与原历史导入维护角色对齐，保留普通员工/API 的导入边界。

## 真实 HTTP 揭示的权限开销

首批真实读取中，管理员已缩小到约 8.3 KB，但教师仍需 1.5–2.2 秒。执行计划显示：线索 RLS 的协作兜底 `can_view_school_lead` 对约 4,000 条线索逐行计算；总览中的线索、沟通、来源提交又各执行一次，三段各约 0.42 秒。

此前的前置权限与管理员快捷分支仍在，协作兜底尚未批量化。新增 `20260921008000_overview_lead_pool_visibility` 复用已有 `school_list_visibility`，仅替换该兜底的可见 ID 集合。原快捷分支、另外两条测评/邀约 SELECT 策略及写权限保留。新函数仅使用当前调用者身份，不能传入其他身份；查询之间不缓存可见集合。

六个固定角色的 Lead、沟通、来源提交完整 ID 集合，在修改前、修改后及恢复旧策略后三方一致；prepared statement 的管理员→教师→管理员切换也一致。权限定义及依赖函数摘要在迁移中设有漂移保护。

## 统计与写入验证

固定 `now=2026-09-21T04:12:37.123Z`，使用真实 Supabase 身份和旧应用算法对照管理员、校长、教师、教研共 20 组当前/历史周月：计数、每日趋势、缺日期与人员归属全部一致。另有 11 组来源标签、14 组日期与空白字符边界。

学生、家长不能取得统计事实；匿名和 service_role 没有聚合接口执行权。同一 prepared statement 切换身份不残留管理员结果。生成字段使用普通员工、服务角色和原历史导入维护角色检查；真实首联 `record_lead_contact_v2` 保存成功。版本重选、来源范围退出/恢复、异常原文和月份状态更新均在回滚夹具中验证。

隔离事务结束后，原业务内容、表 owner/ACL/RLS、列、策略、视图、函数与账本摘要恢复。第二条补丁保存了独立恢复 SQL，并实际恢复旧策略后重测集合。未创建新测试账号，夹具均已回滚。

## 迁移与测量范围

本机 preflight 核对 WhiteHouse、loopback Supabase、监听进程、Docker 网络和数据库系统指纹。首条迁移实际执行约 **8.12 秒**，三表物理占用从 93,487,104 到 89,964,544 字节，窗口内 WAL 增量约 84.30 MB；物理占用包含重写整理的影响，WAL 是窗口观察值。业务原文摘要不变，记录不被替换或删除。新增 STORED 列会重写并持有表锁，生产窗口按目标规模重新评估。

首条接口 SQL 连续样本约 **82.6–84.1 毫秒**，结果 JSONB 8,298 字节。真实读取器包含时区与汇总两次 HTTP，请求正文合计 8,313 字节；首次管理员读取约 263 毫秒，后续约 103–109 毫秒。这里未清空数据库缓存，也没有测量页面渲染。首次值仍需与完整路径一并优化。

本次旧基线直接调用 `getStaffOverviewData`，管理员样本 37 次、8,790,591 字节。此前 39 次、8.85 MB 的采集还包括工作项与月目标。旧基线涵盖完整总览，新接口目前只覆盖两个指标，性能与字节数按各自范围登记。

第二条权限补丁应用后，20 组真实 HTTP 的指标结果仍与原算法一致，另重复管理员当前月 5 次。管理员在该测试进程中的首个读取 **172.3 ms**，5 次后续为 **97.9–105.5 ms**；教师四个周月分别为 **390.8、374.2、364.1、363.8 ms**，比修复前的 1,501–2,244 ms 明显下降。每次均只调用时区和汇总两个 RPC；当前月管理员合计 8,313 字节。没有清空数据库缓存，样本量不足以声明生产 p95。

教师仍超过完整数据读取的 250 ms 设计预算，剩余权限集合与其他指标统一读取继续在 C+D 优化。上述计时从已登录客户端的读取开始，包含 HTTP 接收和类型校验，未覆盖登录、应用模块首次加载、RSC 传输及浏览器可操作时间。

新读取器的错误/零值合同、真实数据库、真实 HTTP、定向 ESLint、TypeScript、数据库类型生成摘要及文本检查均通过。本轮没有 UI 接入，不重复页面构建或把接口测试当作页面验收。
