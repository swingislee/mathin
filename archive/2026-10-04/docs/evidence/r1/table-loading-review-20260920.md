# 表格加载优化复核：发布、回退与剩余读取成本

> 2026-09-20 复核。生产只读；本机函数对照在事务中回滚，未新增持久数据库变更。
> 结论：已有优化确实保留并降低了局部成本，但尚未完成表格读取结构的整改。最新应用补丁仍是开发状态，不能视为生产性能问题已解决。

### 1.2 历史上确实发生过覆盖回退

[9 月 14 日调查](dashboard-collaboration-read-regression-20260914.md)确认：生产先部署性能迁移，随后补入编号更早的协作迁移，把 `leads_select_pool_scope` 改回逐行调用权限函数。开发按编号顺序应用，生产按实际发布顺序应用，导致同一份源码出现不同最终策略。`219eb3e1` 已修复，本轮确认直接可见分支仍存在。

同一时期学生 base helper 也出现协作定义差异；[9 月 15 日补丁](student-list-deep-read-20260915.md)已对齐。本轮核对没有发现它再次被覆盖。

另一种回退来自页面重新组合：`e5aa5d58` 将沟通切换为学生阶段列表，并在外层列表查询完成后加载内嵌首联。原来的外层筛选候选、重复记录提示仍被计算，但内嵌表并不消费它们。`e8a941cb` 去掉了这部分重复工作。它不是原 SQL 被改回，而是新入口重新叠加了读取成本。

### 1.3 过去的测量覆盖不一致

- SQL、完整 HTML/RSC、浏览器名单可见、可操作分别是不同指标。历史亚秒 SQL 或本机 HTTP 不能证明生产首屏达到两秒。
- 管理员、具有全局读取权限的员工、受限员工分别走不同分支。[实际生产浏览器诊断](dashboard-browser-first-load-20260920.md)的固定账号在生产为受限 staff，普通刷新也约 8.8 秒；不能继续统一归因于首次缓存或 Storage。
- 直接表 SELECT 的 RLS 与 `SECURITY DEFINER` 名册 RPC 的内部显式授权是两条路径。优化 `students` 的 SELECT 策略，不会自动消除 RPC 内部再次调用权限函数的成本。
- 上轮浏览器复测覆盖默认沟通首联与测评，没有证明沟通五个标签及全部筛选／翻页状态都达标。

## 2. 本轮真正改变的层次

| 层次 | `e8a941cb` 改动 | 仍存在的成本 |
| --- | --- | --- |
| 沟通权限 | 请求内批量计算可见身份，减少逐条重复调用 | 仍需推导阶段、汇总事实；全范围读取随数据量增长 |
| 首联查询 | 省去内嵌表未使用的提示和外层 facets | 只对满足条件的首联走简化分支；其他标签及筛选分支保留完整计算 |
| 测评服务器到浏览器 | 全量筛选后只发送当前页，编辑器按展开加载 | Supabase 到服务器仍读取全量事实及关联数据 |
| 沟通业务范围 | 清理旧工作批次切换，按实际业务阶段找人 | 管理员默认首联从旧工作集合 98 条扩大为阶段集合 2278 条，不能沿用旧小集合的性能基线 |

因此，本轮的核心是减少重复授权和首屏传输；测评尚未完成数据库分页。

## 3. 重新实测发现的深层问题

### P1：测评每次搜索和翻页仍全量重读

在本机隔离库复用固定管理员，完整执行当前服务端读取器后再调用当前分页函数：

| 页面状态 | 读取记录 | REST/RPC 请求 | 接收字节 | 返回页行数 |
| --- | ---: | ---: | ---: | ---: |
| 当前记录首页 | 930 | 110 | 2232032 | 50 |
| 第二页 | 930 | 110 | 2232032 | 7 |
| 搜索无结果 | 930 | 110 | 2232032 | 0 |

当前范围实际只有 57 条，仍读取包括历史在内的 930 条。教师同样读取 930 条，109 个请求、1470703 字节。当前 `assessments/page.tsx` 在解析页面范围后仍无参数调用 `listAssessmentWorkbenchRows()`，范围和分页在返回后才应用。

新分页将原客户端筛选改为 `router.replace`，250 毫秒搜索防抖和 180 毫秒列条件防抖减少了触发次数，但每次导航仍执行完整读取。因此首屏变小，同时新增了服务器端的搜索／翻页读取开销。相关读取器没有传递业务查询取消信号；是否因快速输入留下并发旧读取尚未在生产实测，列为需要验证的风险。

### P1：四批并发不是整页并发上限

管理员单个测评读取峰值为 30 个同时在途请求，教师为 29。原因是多个关联表同时各自启用四批并发。管理员本机暖读取约 184 毫秒；每请求额外模拟 40 毫秒后为 737 毫秒。此模拟仅证明仍对传输等待敏感，不是生产耗时或并发压测。

其中 64 个来源记录为取学服姓名读取了约 463 KB 原始来源内容；报名主体约 790 KB，测评结果约 466 KB。只按需取列表字段、在数据库选择当前页，比继续增加并发更直接。

### P1：沟通其他分支尚未达到同一优化程度

管理员“待测评”仍需汇总 2329 条，再计算完整字段候选和当前页提示。本轮首次完整读取样本 2614 毫秒；随后单 RPC 三次为 1290 / 1166 / 1260 毫秒，不含布局、认证及浏览器绘制。首联简化 RPC 同轮为 822 / 720 / 690 毫秒。不得把上轮默认首联的 1.07–1.86 秒推广到全部沟通页面。

`communication/page.tsx` 对工作单、联系人、`view` 参数以及缺少学生列表权限的账号仍进入 `CommunicationWorklistPage`。这条路径在 `communication-workbench-data.ts` 中先按 `unpaged: Boolean(fieldOptions)` 补齐候选详情，再进行字段分页。它没有获得本轮首联简化查询的收益。

线索入库也保留“全部 ID → 全部关联详情 → 字段筛选 → 当前页”的结构。本轮当前运营范围 198 条读取 29 次、约 217 KB，暂未慢到数秒；此结果不能证明更多记录时仍稳定。

### P2：旧 `.limit(5000)` 仍可能静默截断

`leads.ts` 的来源、兴趣、沟通、邀约关联读取仍使用 `.limit(5000)`，部分关联读取没有分页。已使用本机真实 REST 只读核实：请求 5000 条、可见总数 4001，实际仅返回 1000 条，受 REST 服务端上限约束。

本轮页面关联样本没有达到 1000 行，**未发现当前页面实际缺行**；这里是已确认存在的读取上限风险。数据增长后可能丢失较早的关联记录，进而影响最后联系、来源数量和筛选候选。应改为完整有界批读，或在数据库直接返回当前页需要的最新／聚合结果。

### 已修复：静态审计漏掉导入别名

`assessment-workbench-data.ts` 将 `readRelatedAssessmentRows` 导入为 `readRelatedRows`，原扫描器只匹配原名。实际复核前该模块仅识别 5 个调用点，修正后为 25 个；新增 20 个真实调用点，原结果无丢失。

当前全清单为 76 个 Dashboard 入口、11 个 API 补集、1011 个保守可达调用点。调用点仍不等于首屏实际请求数，也没有覆盖 SQL 函数内部的所有执行成本。新增回归测试验证别名与原名得到相同的读取清单；本轮测试、Node 语法及相关 ESLint 通过。

### 已排除的一个疑点

额外怀疑批量可见集合会拖慢小范围读取，已在本机事务中换回原函数对照，再完整回滚。1／3／50 个指定主体的结果一致，前后约 96–107 毫秒，没有发现数量级回退；固定教师“我的待报名／待续班”反而由约 4.2–5.7 秒降至 60–85 毫秒。函数目录摘要回滚后一致。这支持保留本轮权限优化，但不消除上述全量事实读取问题。

## 4. 后续整改应围绕同一个数据边界

1. 为测评、线索、沟通工作单建立列表摘要读取：数据库完成权限、当前／历史范围、搜索、排序、全局候选和分页，再补当前页的显示字段；展开时读取详情。保持全量筛选语义，不能直接截取前 50 条后再筛选。
2. 沟通五阶段分别测量。阶段数量、筛选候选与当前页详情拆开核对成本，避免每次翻页重复构造完整宽记录。
3. 为“读取一页”设定请求数、返回行数和字节量的回归预算。覆盖无权限空结果、部分权限、大范围、首页／末页／搜索无结果、历史范围以及快速切换。权限和结果等价测试继续保留。
4. 发布从实际生产账本演进到候选，检查最终策略／函数定义和关键读取计划，覆盖后补迁移的应用顺序。机器检查、生产发布与真实浏览器验收分别记录。

本轮未继续堆叠应用层缓存或业务补丁，也未发布生产。此前候选的默认页改善有效，但“全表格读取优化完成”的结论仍不成立。
