状态：**生产只读审查完成；签名传输补丁的机器检查通过，尚未部署。** 当前生产仍为 `1eaab0fb`。本次不改变数据库、Storage 配置、服务进程或业务数据，不关闭 R1-Live-2，也不宣称页面已达到 2 秒。

## 结论

用户要求仔细审查[上轮记录](dashboard-query-production-20260920.md)中的 Storage 首次 2.8 秒，核对它是否解释“首次很慢，后续变快”。异常真实存在，但它来自运维 HEAD 探针，当前证据无法将其归因为真实首屏的 Storage 冷启动。另一个可复现的问题是：服务端生成资源签名地址仍绕公网，增加了首请求和热请求的网络等待，已准备局部修复。

## 2.8 秒样本实际测到了什么

- 2026-09-20 09:04:32.777 北京时间结束的 `object.head_authenticated_info`，探针总耗时 2797 ms，Storage 日志 `responseTime` 为 2721.980 ms。`executionTime=2710` 从 `onRequest` 到 `onSend`，包括插件、身份处理和路由逻辑，不能解释为单条 SQL 或文件读取耗时。
- 请求使用运维 `service_role`，方法为 HEAD；不是浏览器图片 GET，也不是页面等待的批量签名 POST。
- 核对生产实际安装的 `getObjectInfo.js`、`renderer/head.js` 和公共 `renderer.js`：该接口查询 bucket/object 元数据，再从 `object.metadata` 生成响应头，**不调用文件后端读取图片或做文件 stat**。因此这个样本不能证明磁盘图片冷读取耗时 2.8 秒。
- 对应对象元数据查询在 `pg_stat_statements` 中有 17 次调用，执行时间最大 1.685 ms、均值 0.328 ms。规划时间未采集；连接获取、请求插件及其他等待也不在这项 SQL 执行统计里，不能据此排除全部数据库等待。
- 慢请求结束时刻与上轮迁移演练回滚完成窗口重合。本机/生产时钟的 SSH 区间对照支持时间重合，但服务身份下元数据查询的锁关系没有出现演练修改的 `session_events`；**没有证据证明演练锁阻塞就是原因**。当时缺少分段 trace，准确阻塞点仍未知。

Storage 容器使用 `supabase/storage-api:v1.60.4`，从 7 月 17 日连续运行，重启计数为 0；实际存储后端是同机 ext4 文件系统。数据库直连同机 PostgreSQL，连接池最小连接数 0，默认空闲连接回收为 60 秒，池实例本身复用。自然空闲约 13 分钟后，同一组 HEAD 首条为 55 ms，其余 6–11 ms，未复现秒级延迟。以上核对没有重启服务、清缓存或人为制造数据库锁。

## 已确认的服务端签名绕公网

`loadCoursewareSharedAssets` 在页面返回前等待资源 RPC、预览元数据和批量签名。现有 `createSupabaseServerFetch` 只将 Auth/REST 请求转到 `127.0.0.1:8000`，Storage 签名仍请求公开 HTTPS origin。

在生产主机上，对同一组 5 个首页图片执行两轮低频交替探测，分别让公网/同机请求先执行。签名有效期 30 秒，结果在主机内验证后丢弃；没有下载图片，也没有导出地址或凭据。使用服务权限仅用于隔离传输差异，不是普通用户权限或页面计时验收。

| 轮次 | 该传输在进程中的首请求 | 后续请求 | 说明 |
| --- | ---: | ---: | --- |
| 公网先执行：公网 | 369 ms | 51、47 ms | 首次 Kong upstream 为 134 ms |
| 公网先执行：同机 | 14 ms | 8、8 ms | 此时 Storage 已被前一个请求访问 |
| 同机先执行：同机 | 83 ms | 22、9 ms | 自然空闲后执行，首次 Kong upstream 为 17 ms |
| 同机先执行：公网 | 192 ms | 56、46 ms | 此时 Storage 已被前一个请求访问 |

两轮都显示公网的额外开销；顺序和缓存状态不同，**不能把 369→14 ms 当作同条件冷启动收益，更不能当作页面提速幅度**。首轮公网首请求中，扣除 Kong upstream 后约 235 ms 位于其余传输/客户端环节，无法进一步精确拆为 DNS、TCP、TLS 各项。热请求公网约 46–56 ms，同机约 8–22 ms。

补丁只增加同一 Supabase origin 的 `POST /storage/v1/object/sign/` 转发，覆盖单个和批量签名。继续使用请求原有用户凭据，保留 Request 的方法、body、cache、signal 和 caller override。SDK 仍以公开 origin 生成最终资源地址；资源 GET、上传、删除和其他 origin 沿用原传输，失败原样返回。
