# 总览与线索读取的权限前置判断 · 2026-09-20

状态：**修复已应用开发数据库，定向机器检查通过；生产未部署，生产首屏待复测**。本轮不关闭 R1-Live-2 或正式 Gate。

## 问题与实现

[生产浏览器实测](dashboard-browser-first-load-20260920.md)发现，授权测试账号在生产为受限 staff。总览数据约 8.8 秒出现；线索查询为返回空结果，仍逐条检查 3942 条线索，单次约 6.84 秒。

迁移 `20260920130000_dashboard_lead_read_guards` 在三个现有 SELECT 策略前增加独立子查询中的必要权限判断：

- 线索池：先判断 `followup.view` 或 `student.import`；
- 受邀测评及历史测评：先判断 `review.write`。

缺少必要权限时，CASE 直接返回 false；满足条件时执行完整的原策略。账号权限在当前 SQL 查询内求值，继续保留逐条归属、参与、分组、邀请和测评历史规则。身份、权限分配、写策略、辅助函数、ACL 和业务记录保持原样，没有建立跨请求的权限缓存。

迁移先核对三个辅助函数的完整函数体、稳定性、security definer 属性，以及三个原策略的表达式、角色和类型。授权规则发生漂移时迁移报错，要求重新核对前置条件。

## 开发验证

`scripts/dashboard-lead-read-guards.mjs --check` 使用既有本机目标核对器，检查执行主机、应用实际 Supabase origin、监听进程、Docker endpoint／网络和数据库指纹后才运行。验证使用真实 PostgreSQL 与 RLS，复用 manifest 中 11 个固定身份及匿名角色。

- 对线索、当前运营线索、沟通事实、线索来源及报名机会五类读取，比较迁移前后全部可见记录的数量和有序 ID 摘要，60 组一致。
- 固定员工在隔离事务中撤销岗位权限、停用及要求改密，15 组读取结果一致。场景修改分别回滚，没有创建账号。
- 多个账号连续执行同一组预备语句，并强制使用 generic plan，验证账号切换及权限变化后仍按当前声明读取。
- 恢复原策略后再对照 60 组结果，全部一致；验证事务回滚后，业务、函数、策略、关系权限与迁移账本摘要恢复原状。
- `--apply` 随后应用相同 checksum 的迁移至开发数据库，登记账本并复读。仅三个策略表达式发生变化，业务数据和其他结构摘要一致。
