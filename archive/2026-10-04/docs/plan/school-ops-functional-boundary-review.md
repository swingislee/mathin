## 1. 重审结论

**当前规划已经区分了不少底层业务事实，但页面的职责逐步扩张，缺少统一的功能边界。**

学生页按人和阶段组织，学服按环节组织，活动按场次组织，班级围绕稳定的教学组织展开。它们描述的是不同的查找和工作方式。后续规划又让这些入口各自承载沟通、测评、报名、续班等登记，于是多个页面看起来都能办理同一件事，却没有完整说明：哪些只是同一能力的入口，哪些拥有独立的业务结果，哪些只负责汇总其他地方的结果。

重审需要先回答三个问题：一项功能负责哪一件事；它保存或改变什么事实；什么结果表示这件事完成。页面位置和角色默认入口随后确定。

本次发现可以分为三类：

| 类型 | 具体发现 | 审查判断 |
| --- | --- | --- |
| 真实的业务差异 | 报名与入班；活动到场与测评结果；当前班级成员与历史课次记录；课后沟通与招生沟通 | 保留不同事实及完成条件，可以在同一工作面连续办理 |
| 同一业务的不同视图 | 跨场次测评与某场活动中的测评；班级组织总览与个人班级；学生详情中的各类历史 | 共用记录与操作含义，明确每个视图的筛选范围和用途 |
| 需要纠正的边界混用 | 用学生主阶段推断报名类型；把全体有效在读关系命名为待续班；不同入口对报名与缴费采用不同确认条件 | 先统一业务含义，再决定页面合并、移动或保留 |

因此，“只留一个班级页”和“把学服拆成首级菜单”目前都不足以成为完整方案。可先确定共同的班级入口和业务能力归属，同时保留确实服务于不同工作的视图。

## 2. 功能边界的建议定义

下表划分业务职责，不等于增加九个菜单，也不要求一次实际沟通拆成多次保存。一个详情面板可以同时调用多项能力，结果分别回到对应的业务记录。

| 业务职责 | 一条记录代表什么 | 应负责的动作与结果 | 与其他职责的交接 |
| --- | --- | --- | --- |
| 身份与客户资料 | 一个人、家庭或尚未确认身份的线索 | 确认身份、维护联系方式、负责人及来源；形成可持续关联的主体 | 活动、报名、班级共用身份；查到这个人不等于产生待办 |
| 沟通与邀约 | 一次联系、一次预约安排或明确的后续约定 | 记录联系事实、邀约场次与时间、需要再次处理的事项 | 到场由活动参与事实确认；课程报名由报名动作确认 |
| 活动参与 | 某人在某一场活动中的一次参与 | 报名活动、预约、到场、缺席及取消，保存本场安排 | 可关联测评、课堂表现和课程意向；重复参加产生新的参与记录 |
| 学习测评 | 某次实际测评尝试及其专业结果 | 记录测评过程、结果和教师建议 | 同一结果可在测评列表、活动和学生详情显示；邀约完成不等于测评完成 |
| 课程报名 | 某人针对某课程、某期次的一次报读关系及其前置意向 | 意向、确认报名、缴费依据、结束或变更关系 | 报名后可等班；入班和实际出勤分别确认；确认报名的统一条件见 §4.3 |
| 班级组织 | 一个开班实例，以及某人在其中的一段成员关系 | 开班、教师责任、容量、排课、入班、调班、座次和成员变动 | 读取报名资格，向课次提供名单；保存班级变动不重写已发生的课次 |
| 教学履约 | 某一课次及其中学生的学习、出勤和课后结果 | 备课、行课、点名、观察、作业、课评与课后沟通 | 从班级或待办进入同一课次；内部记录与面向家长发布的结果分别处理 |
| 续班专项 | 某轮续班中，由既有课程／在班关系转向目标课程与期次的处理事项 | 组织本轮对象、记录意向和跟进、确认本轮结果 | 正式报名调用课程报名能力；本期在读关系继续存在 |
| 工作协同与汇总 | 有负责人和处理目的的任务，或对业务事实的查询结果 | 组织工作名单、到期安排、教学完成情况和管理统计 | 业务动作产生结果，任务和统计引用结果；手工任务本身只确认工作安排 |

这延续了 [doc 30](30-mathin_school_ops_architecture_plan.md) 的身份、参与、测评、报名、班级成员与课次区分，以及 [doc 25](25-production-1.0-product-completeness.md) 的领域事实与工作项投影原则。需要补齐的是各入口调用这些职责时的规则。

## 3. 以班级为例：哪些可以合，哪些要保留

### 3.1 目前三个工作面处理的范围不同

| 工作面 | 实际观察范围 | 独有价值 | 与其他工作面的重叠 |
| --- | --- | --- | --- |
| 学服中的分班 | 学期、年级下的待分班对象、现有班级、成员与座位 | 横向比较班级容量，连续安排入班、调班和座次 | 班级名单、教师、学生摘要、报名与续班提示 |
| 班级列表及班级详情 | 一个班级的持续存在、当前组织情况和相关课次 | 管理班级、排课、成员及长期入口；包含尚无所选期间课次的班级 | 班级、学生和课次摘要 |
| 教学工作台的班级概览 | 所选周／月／学期内的课次，再按班级归组 | 连续查看和登记教学记录，汇总出勤、观察、课评与沟通 | 班级、教师和学生摘要 |

代码依据：[分班工作面](../../src/features/school/EnrollmentPlacementWorkbench.tsx)、[班级列表](../../src/features/school/ClassroomList.tsx)、[个人班级表](../../src/features/school/PersonalClassroomTable.tsx)、[教学班级归组](../../src/features/school/teaching-workbench/teaching-class-overview-contract.ts)。

教学班级概览从所选范围内的课次生成，学生数是这些课次学生 ID 的去重数。当前班级名单则回答现在有哪些成员。调班后，一个学生仍可能计入原班的本月教学记录。两者都显示“班级人数”时，应先明确口径，才能放到同一工作面。

此外，当前代码的个人班级已经使用表格，旧规划中“个人班级保留信息卡”的描述需要更新。卡片改成表格已经发生，入口职责重叠仍需单独解决。

### 3.2 建议的边界

**可以确立一个共同的班级入口，并在其中提供“组织安排”和“教学记录”等视图。**

- 班级名称、教师责任、排课及成员关系采用共同的对象和操作定义。
- 组织安排保留分班页的学期／年级横向布局、等班区、容量和连续操作价值。
- 教学记录保留日期范围、历史课次名单、教学记录以及对应的统计口径。
- 教师默认进入其实际工作范围；学服进入其组织范围。可见班级、可查看学生资料和可确认报名分别按实际授权判断。
- 每次课仍进入既有课次工作区；从多个入口打开时定位同一课次。

这是对共同入口的建议。具体采用一个页面内切换、列表与详情分工，还是保留跨班教学汇总，需要在上述职责确定后验证。**分班页可提供共同工作面的主要组织方式，其覆盖范围仍需补上班级设置与教学履约。**

## 4. 已发现的关键边界问题

### 4.1 学生主阶段承担了超出其范围的业务判断

[学生阶段规划](student-stage-workspace.md) 把五个主阶段定义为互斥，并把任何仍有有效报名或在班关系的学生归到“待续班”。这个集合包含等班、正常在读、本轮不续但仍在读等情况。

而 [学服升级方案 §3.2、§7](mathin_school_support_upgrade_v2.md) 明确要求按课程和期次判断，允许同一学生同时“秋季数学在读、寒假数学待续班、数独课未报名”。这两套分类可以作为不同层次的观察方式共存，但主阶段不足以确定具体报名业务。

当前 [学生快捷登记](../../src/features/school/StudentStageEntry.tsx) 在未传入专门上下文时，按 `row.stage` 推断 `new / renewal / reactivate`，再按该类型匹配课程商机。代码中的默认推断已把人的综合分类用于决定某门课程的业务类型。

**建议：学生主阶段只用于概览和查找；报名类型由所选课程、期次和已有报读关系确定。** “待续班”工作范围应对应真实续班事项，正常在读和等班可以作为独立筛选条件。现有学生页的工作名单、全部记录、重新联系三种范围继续保留其各自含义。

这是静态发现的语义风险，本次没有据此认定发生了实际错报，也不自动调整已有报名数据。

### 4.2 学生页的“续班”和专门续班工作表缺少完整的共用约定

专门续班工作表以“续班周期＋原班级成员关系”定位事项，并保存本轮结果和修订版本。学生快捷报名以“学生＋课程＋期次＋报名类型”匹配商机，提交不携带续班周期和原班级成员关系。

两条路径可能复用同一条已有关联的商机，但这些条件不足以证明任意一次新增续班都能被两处等价处理。

**建议：从学生、班级或续班工作表办理同一轮续班时，传递同一份续班事项上下文。** 跨入口共用目标课程、期次、原关系、本轮结果及修订约定。没有具体续班上下文时，先按目标课程关系确定办理事项。

依据：[学生保存事务](../../supabase/migrations/20260908000100_student_stage_workspace.sql)、[档案保存包装](../../supabase/migrations/20260908008000_unified_student_records.sql)、[续班保存事务](../../supabase/migrations/20260907000300_renewal_workbench_details.sql)、[续班对象池](../../src/features/school/RenewalStudentPool.tsx)。

### 4.3 “报名成立”和“已缴费”存在尚未统一的产品规则

[学服升级方案 §5.4](mathin_school_support_upgrade_v2.md) 采用“先缴费确认学位，有班入班、无班等班”。学生快捷登记确认报名时也要求填写缴费确认依据。

[续班工作表说明](../runbooks/renewal-workbench.md) 则明确区分“已报名”与“已缴费”，允许确认报名时尚无缴费记录。对应事务的 `registered` 分支会确认课程报名，`paid` 分支另行登记实际缴费。

**两条路径对报名成立条件的定义不同。这是跨入口统一前需要先解决的产品规则。**

建议继续分别保存意向、报名、缴费依据和入班事实，并统一确定：未缴费的报名是否成立；是否占用容量；何时允许入班。如果不同课程有不同政策，应由显式政策决定，保存时使用相同规则。

本稿保留这一决策点，现有不同路径均不被默认为全局权威。人工记录缴费事实也不等于启用完整收款、退款或财务系统。

### 4.4 “分班”名称掩盖了其已经扩大的承载范围

分班页已经包含班级组织、待分班、座次、调班、学生摘要及续班健康提示。它好用的原因至少包括：把班级、学生和容量关系直接放在同一个工作面，支持成批观察和处理。

其中有三种不同职责：

- 报名确认某个学生报读什么课程、哪个期次。
- 班级组织确认学生在哪个班、由谁带、如何排课和安排座位。
- 健康与续班提示引用其他业务事实，帮助组织者决定下一步。

**建议把分班中的组织能力确认为班级组织职责，报名及续班通过共用能力就地办理。** 这样它可以服务教师、学服与管理者，保留现有工作效率，同时明确哪些动作实际改变报名或续班结果。

尤其要区分已报名但未入班的人，以及已有实际在班关系、历史商业资料尚不完整的人。页面整合应保留各自真实情况。

### 4.5 测评和活动有合理交集，共同记录的范围应明确

测评工作台是跨场次的测评队列，当前读取也覆盖关联活动；活动页围绕一场活动组织参与者与现场工作。两处展示同一次测评是合理的。

需要分别确认的是邀约、活动参与和专业测评结果。例如“预约已确认”“已经到场”“测评已完成”各有真实依据；同一孩子第二次来测评产生新的尝试。

**建议共用同一次参与／测评记录和专业写入规则，保留跨场次与单场次两个工作范围。** 现场可以一次保存相关事实，学生详情汇总原记录。普通活动登记权限与专业测评结果的写权限分别判断。

依据：[测评队列读取](../../src/features/school/assessment-workbench-data.ts)、[doc 30 §0A、§4.4、§8.3](30-mathin_school_ops_architecture_plan.md)。

### 4.6 “沟通”共用文字字段，也可能具有不同完成条件

招生联系、独立备注和课后沟通都可能包含文字、日期和后续安排，但课后沟通还关联具体课次名单及该课次的完成状态。

当前课次沟通已经复用 `student_follow_ups` 保存逐生记录，另有班群沟通，并通过课次上下文判断完成。说明表或组件的共用已经部分存在，需要继续明确业务关联。

**建议统一基础记录能力，按实际事项附带上下文。** 普通备注可以独立保存；课后沟通保留课次、当时名单、跟进结果及完成判断。学生详情可统一查看历史，业务统计按原始记录与实际联系去重。

依据：[课次沟通迁移](../../supabase/migrations/20260915008000_session_communications.sql)、[完成条件](../../src/features/school/session-communication-contract.ts)、[学服升级方案 §3.3、§6](mathin_school_support_upgrade_v2.md)。首联既有验收行为继续以 [保护基线](school-support-followup-panel-contract.md) 为准。

## 5. 现有入口应承担什么职责

下表给出功能归属建议，便于逐项审议页面去留。

| 现有入口 | 建议保留的核心职责 | 建议收敛的职责 |
| --- | --- | --- |
| 学生 | 查人、了解跨课程完整经历、按真实条件筛选、就地调用业务操作 | 主阶段对所有业务类型的决定权；另起一套报名／续班含义 |
| 首联 | 原始名单的首次联系、身份确认与邀约的连续作业 | 对后续所有学生沟通的包揽 |
| 测评 | 跨场次组织待处理测评、登记专业结果 | 与活动分别保存同一次测评的结果 |
| 活动 | 场次安排、参与者、现场工作；就地完成关联登记 | 以活动页面位置判定学生整体生命周期 |
| 分班 | 班级组织、等班安排、容量、成员及座次操作 | 把整个课程报名和续班过程隐含在“分班”名称里 |
| 班级列表／详情 | 班级的持续入口、组织设置、成员及课次 | 因角色不同复制班级的定义与操作含义 |
| 续班 | 具体周期的目标对象、持续跟进及结果处理 | 把所有正常在读学生直接当成当前续班任务 |
| 教学工作台 | 跨班课次工作、期间教学记录与完成情况 | 再定义一套当前班级名单或班级管理规则 |
| 总览／待办／Student360 | 按角色组织待办、汇总事实、定位原业务记录 | 在汇总层独立修改业务状态或复制登记历史 |

补充：旧 `/dashboard/assessments`、`/dashboard/enrollments`、`/dashboard/renewals` 当前是到学服对应路径的跳转入口，不能据路径数量算作三套重复实现。

## 6. 学服工作台是否应当拆开

**学服的功能归属可以拆清；工作台本身是否保留，应按集中作业的价值决定。**

学服现在组合了首联、测评、班级组织和续班等工作，它们各自具有业务边界。这个组合可以继续为学服人员提供连续处理入口，而各能力由共同的业务规则支持。

具体建议：

1. 班级组织作为共同能力，允许学服与教师按授权使用。
2. 首联和续班保留目的明确的批量工作面；测评保留跨场次的专业队列。
3. 学生和活动中的快捷登记调用同样的业务能力，完整传递办理事项上下文。
4. 教学工作台继续组织跨班教学工作；其班级、课次和学生链接进入共同对象。
5. 顶层菜单最后根据常用工作与查找方式安排。角色名称、业务环节和对象名称不再同时承担定义功能边界的任务。

原规划解决的是多张名单来回复制、无法连续登记的问题。调整入口时，需要继续保留已经有用的批量表格、行内登记和一次保存能力。

## 8. 用这些业务情形检验边界

这些是后续设计的检查情形，本次未把它们登记为已执行测试或已验收结果。

| 情形 | 设计应给出的结果 |
| --- | --- |
| 同一孩子秋季数学在读，同时续报寒假数学、首次报名数独 | 三项关系同时成立；学生总体阶段不替代每项业务的类型 |
| 已确认报名，暂时没有班 | 能在报名、学生与等班范围查到；班级人数只计算实际成员 |
| 学生月中从甲班转到乙班 | 当前组织反映乙班；甲班本月已发生的课次和记录保留 |
| 一次测评从活动和测评工作台分别打开 | 两处定位同一尝试；修改回到同一记录，第二次测评另有记录 |
| 同一次沟通产生一个续班意向和一个活动邀约 | 联系事实可追溯一次；两个业务结果各自关联、独立推进 |
| 教师通过共同班级入口处理本班工作 | 获得实际授权的学生与课次能力；报名确认及其他资料按各自权限提供 |
| 正常在读学生暂无本轮续班安排 | 可以从学生或班级查到；工作队列只在存在具体处理事项时纳入 |
| 续班已报名但未缴费 | 所有入口采用已确定的同一政策，报名、缴费、容量和入班状态各有清晰依据 |
