> **裁决去向**：2026-08-14 已将“尽快进入真实使用”的核心决策纳入 active doc 00/04/25；当前 Gate、状态和施工顺序以 doc 04 为准。本文件保留为讨论来源，不直接授权生产操作。

## 0. 当前上下文

Mathin 当前已经经过较长时间的持续开发，后台、课件、课堂、学生/家长端、权限、数据维护、空间数学等多个方向都已经有较多实现。

最近一次对仓库的系统审阅以 `main` 分支最新提交 `7ab92f2` 为基准。审阅范围不仅包括 `docs`，也包含了真实关键代码路径，包括：

- 认证与权限
- Dashboard 路由、导航与工作台
- 学员、班级、课表、财务
- 课件文档模型、编辑、保存、发布
- release / session pin / freeze
- classroom actions 与 LiveShell
- Spatial Math / 3D
- attempt / evaluation
- 学习结果
- H5、Webhook、CSP
- 健康检查、错误记录
- Vitest、Playwright、CI、数据库 replay、RLS 测试
- Terms、Minds、Games 内容和代码

审阅后的一个总体判断是：

> Mathin 已经具备相当完整的工程基础，但“真实上线”这件事没有被单独抽出来作为一个明确、有限、可以结束的项目。

---

# 一、最初的仓库审阅结论

第一次审阅中，主要从工程和产品架构角度得出了以下判断。

## 1. Mathin 当前实际上同时存在三条产品线

### A. 数学知识宇宙

包括：

- Terms
- Minds
- Games
- 数学概念网络
- 概念路径
- 星球 / 岛屿等视觉表达

这一部分是 Mathin 最有辨识度的长期产品方向，但当前仍然存在大量内容为 stub、内容深度不足、与真实课堂学习数据联动不够的问题。

### B. 教学执行平台

包括：

- Courseware Studio
- CoursewareDocument
- 不可变 Release
- Session Pin / Freeze
- Classroom Runtime
- Spatial Math
- Attempt / Evaluation
- Learning Result

这一部分目前是代码成熟度较高、最近施工最密集的领域。

### C. 校务运营系统

包括：

- 学员
- 班级
- 排课
- 跟进
- 财务
- 活动
- 员工
- 权限
- 数据维护
- 系统管理

这一部分功能面已经相当宽。

第一次分析因此提出：

> 后续应避免继续无限扩展模块，而应把 Terms → Courseware → Classroom → Attempt → Learning Result → Student/Parent 的学习闭环作为主轴。

这个判断在长期产品架构层面仍然成立。

---

## 2. 第一次代码审阅中发现的工程问题

包括但不限于：

- 认证关键查询可能存在 fail-open 风险
- 某些首页通过 `safe(promise, [])` 把错误伪装为“空数据”
- CI 很强，但真实完整教师工作流的 E2E 证明还不够
- Terms / Spatial Math 之间的 concept ID 合同还没有完全统一
- `LiveShell` 与 `classroom/actions.ts` 职责越来越重
- Courseware 富文本可能存在语义 round-trip 风险
- “今日”业务日期缺乏明确组织时区
- 当前有 liveness，但 readiness 还可以加强
- 提交历史逐渐代替了真正的产品决策队列

这些建议本身仍然有价值，而且很多可以直接交给 Agent 逐步修复。

但是，后续讨论确认：

> 这些并不是当前用户“迷茫”的根源。

---

# 二、真正的根源问题

用户进一步明确了自己的真实诉求。

## 1. 当前最迫切的目标不是继续完善架构

用户希望：

> Mathin 尽快上线，真正给公司里的老师使用。

现在最大的问题是：

- 所有账号仍然是测试账号
- 产品还没有进入真实工作环境
- 老师还没有真正使用
- 因此也没有来自真实使用过程中的问题反馈

用户并不要求上线前把所有内容全部补深。

对于 Terms、Minds、课程内容深度等部分，用户的判断是：

> 内容本来就是架构上线以后慢慢填充的，不应该成为首次上线的前置条件。

---

## 2. R1 最初的来源

R1 最初的目的并不是“把整个产品做到最终成熟”。

用户对 R1 的原始理解是：

> 主体已经做得差不多，在正式上线前进行一轮维护、修缮、收口，让系统能进入真实使用。

也就是说，R1 本质上应该是：

**上线前维护阶段。**

而不是：

**Production 1.0 全面成熟度认证阶段。**

---

## 3. 为什么现在感觉越来越偏

R1 在实际施工过程中逐渐扩张。

原先只是想：

```text
上线前维护
→ 修核心问题
→ 做一轮稳定性检查
→ 上线
```

但后来逐渐变成：

```text
完整内容盘点
→ 完整内容导入
→ 所有页面完整性
→ 视觉收口
→ 指标体系
→ 全量 E2E
→ 发布审计
→ 备份恢复演练
→ 14 天 RC
→ Production 1.0
```

这导致了一个根本问题：

> 只要没有划定明确的上线边界，Agent 永远都能找到“还可以继续做”的事情。

例如：

- 再补一个权限检查
- 再补一种导入器
- 再做一次审计
- 再增加一套 E2E
- 再完善一个发布状态
- 再加一种 Spatial Math 能力
- 再做一层错误治理

这些工作从局部看都合理。

但：

> 它们不会自动把项目推向“真正上线”。

---

# 三、对“卡在哪里”的重新判断

经过第二轮讨论，重新得出了更准确的结论：

> 当前 Mathin 并不是卡在某一个技术模块上，而是卡在“上线决策没有被单独定义成一个项目”。

也就是说：

- 工程还有很多可以做
- 产品也还有很多可以完善
- 但缺少一个明确规则告诉整个项目：
  - 什么完成以后就算“可以给老师用了”
  - 什么问题可以接受
  - 什么问题才有资格阻塞上线

只要这个边界没有建立，工程就会继续扩散。

---

# 四、需要区分两个“上线”

讨论中进一步把“上线”拆成两个事件。

## 1. 内部生产试运行

这是目前真正需要尽快完成的目标。

特点：

- 使用真实教师账号
- 使用真实组织数据
- 使用真实班级 / 课次 / 业务数据
- 数据不能再像测试数据一样随意清空
- 老师真的把它用于工作
- 出现问题后进入真实反馈和修复循环

它不是 Demo。

也不是测试环境。

而是：

> 小范围、可控用户下的真实生产运行。

---

## 2. Production 1.0

Production 1.0 可以放在后面。

它可以继续包括：

- 更完整的内容
- 更全面的页面
- 更成熟的监控
- 更完整的 E2E
- 更大范围的用户
- 更成熟的备份和恢复
- 更低的人工支持成本
- 更全面的发布审计

因此：

> 原 R1 中的很多工作并不是错误，而是被放错了上线阶段。

---

# 五、3D / Spatial Math 的定位

用户特别明确：

> 最近新开的 3D 模块，是因为当前有真实需求，需要用于一些可视化展示。

它应该和上线主线并行。

也就是说：

```text
主线：Mathin 尽快正式给公司老师使用
并行线：3D / Spatial Math 模块继续发展
```

3D 不应该阻塞上线。

因此后续需要遵守以下原则：

1. 3D 可以继续开发
2. 3D 可以继续合并
3. 3D 应通过独立路由、权限或 feature flag 隔离
4. 普通教师默认不必看到未完成 3D 功能
5. 3D 不进入“内部上线完成条件”
6. 只有当 3D 修改破坏主系统时，它才临时成为上线阻塞问题

核心判断：

> 3D 不是偏离上线目标的根源。真正的问题是此前没有规定“什么才有资格阻塞上线”。

---

# 六、第一次提出的“日期驱动上线”为什么不适合

第二轮讨论曾经提出过：

- 选定某个具体日期
- 倒排：
  - 账号建立
  - Smoke Test
  - 正式教师试用
  - P0/P1 清零
  - 正式开放

这个思路的价值在于：

> 强迫项目做出上线决策，而不是无限维护。

但用户进一步指出：

> 对当前项目而言，不需要日期驱动，更适合“完成项目驱动”。

这个校准是正确的。

因为目前真正需要的是：

```text
某项项目完成
→ 过一个上线 Gate
→ 下一个项目
→ 全部 Gate 通过
→ 立即上线
```

而不是：

```text
为了某个日期
→ 强行压工期
```

---

# 七、最终确定的推进方式：Gate 式上线

新的上线主线命名为：

# R1-Live：真实教师首个可用闭环

它不是替代整个 R1。

它的作用是从 R1 中切出一个：

> 有边界、可完成、完成后立即上线的项目。

---

# 八、R1-Live 的完成定义

## 核心定义

一名公司内部老师使用：

- 正式账号
- 正式组织
- 真实业务数据

能够独立完成一次真实工作。

同时系统满足：

- 数据能够保存
- 权限正确
- 错误可以发现
- 出问题时有最小回退能力

达到这个条件：

> Mathin 就进入内部生产运行。

不需要先完成所有内容。

不需要先完成全部 3D。

不需要先完成整个 R1。

---

# 九、Gate 0：切断无限施工

## 目标

先确定：

> 第一次上线究竟允许老师完成什么真实工作。

建议第一版只选一个最小教师闭环。

例如：

```text
正式教师账号登录
→ 看到自己的组织、班级 / 课表
→ 打开一节真实课程
→ 完成一次实际记录
→ 保存
→ 重新登录后仍然存在
```

实际记录可以从当前实现最成熟的功能里选择一个：

- 出勤
- 课堂记录
- 学习结果
- 课后跟进
- 作业 / 评价

不要求第一次上线同时覆盖所有。

---

## Gate 0 必须得到的结果

所有工作被分成三类：

### A. 本次上线必须完成

只有直接支撑首个真实闭环的事项。

### B. 上线后完成

有价值，但不影响第一批老师工作。

### C. 独立并行

例如：

- 3D / Spatial Math
- 长期内容建设
- 某些实验性质功能

---

## Gate 0 的核心规则

> 不在“本次上线必须完成”清单中的事项，不得自动升级为上线阻塞项。

这是整个 R1-Live 最重要的规则。

---

# 十、Gate 1：正式身份与真实数据成立

目前用户最明显的心理和产品边界是：

> 所有账号仍然是测试账号。

因此第一个真正需要跨过去的工程节点，就是建立第一套正式身份。

---

## Gate 1 最小内容

至少包括：

```text
1 个正式组织
1 个正式管理员账号
1 个正式教师账号
1 个真实班级 / 业务单元
完成真实闭环所需的最小真实数据
```

测试账号仍然保留。

但正式与测试必须明确区分。

---

## Gate 1 通过条件

全部满足：

- 正式教师可以正常登录
- 密码重置 / 恢复路径可用
- 教师进入正确组织
- 教师看不到无权限组织数据
- 测试数据不会混入正式业务视图
- 正式数据不会因为开发初始化随意清空
- 正式身份不依赖临时开发捷径

Gate 1 PASS 以后：

> Mathin 已经跨过“只有测试账号”的阶段。

---

# 十一、Gate 2：真实工作闭环跑通

这一阶段不验收整个 Dashboard。

也不验收所有模块。

只验收 Gate 0 中定义的那个真实教师闭环。

---

## 建议验收流程

使用正式教师账号：

```text
1. 从正式登录页进入系统
2. 找到属于自己的班级 / 课表 / 课次
3. 打开相应课程内容
4. 完成一次真实业务操作
5. 保存
6. 刷新页面
7. 退出
8. 重新登录
9. 再次找到刚刚保存的数据
10. 管理员在正确权限范围内能够看到
11. 无权限用户看不到
```

---

## Gate 2 通过标准

不是：

> 代码里有这个功能。

而是：

> 在真实生产配置 + 正式账号 + 正式数据下，完整操作一次成功。

---

## Gate 2 中不应该阻塞的问题

例如：

- 某个非核心页面 UI 不够好
- 某些内容还是空白
- 3D 还没有完成
- 某个不使用的模块还有 Bug
- 某些文案还不够准确

只要不影响首个真实闭环，就不能阻塞 Gate 2。

---

# 十二、Gate 3：最小生产保险丝

内部上线不需要完整企业级运维系统。

但至少必须有最小安全保障。

只要求四项。

---

## 1. 正式数据备份

Agent 必须明确回答：

> 正式数据当前如何备份？

不一定要求复杂自动化。

但必须确定：

- 当前备份方式
- 最近一次备份状态
- 出问题时数据是否能恢复

---

## 2. 代码回退

必须明确：

> 新版本部署出问题后，如何回退到上一个可用版本？

至少应该具备：

- 可确定的稳定 commit
- 可执行回退流程
- 不因回退破坏数据库

---

## 3. 错误可见

老师反馈：

> “我刚才保存失败了。”

此时必须能回答：

> 去哪里查？

最低限度需要：

- 服务端错误日志
- 可定位时间和请求
- 不再把严重错误完全伪装为空状态

---

## 4. 正式数据不被开发脚本误清

正式生产环境必须避免：

- 开发 reset
- seed
- rebuild
- fresh replay

误作用于正式数据。

---

## Gate 3 通过条件

团队能够明确回答：

1. 正式数据在哪里？
2. 最近的备份在哪里？
3. 新版本坏了怎么回退？
4. 老师报错以后怎么定位？

不要求在这一阶段完成：

- 完整灾难恢复演练
- 全量监控平台
- 全量 E2E
- 14 天稳定性观察
- 全部生产成熟度证据

---

# 十三、Gate 4：一名真实老师独立完成

这是上线前最后一个 Gate。

也是最重要的 Gate。

找一名公司内部真实老师。

使用：

- 正式账号
- 正式业务数据
- 真实工作场景

完成 Gate 2 中的闭环。

---

## 用户本人在这一阶段的角色

不是继续审代码。

而是：

> 观察老师能不能独立工作。

尽可能不要边看边教。

重点观察：

- 老师第一步点哪里
- 找不找得到入口
- 哪个词不理解
- 哪一步需要问人
- 哪一步不敢操作
- 哪一步让他觉得和实际工作不一致
- 数据是否保存正确
- 第二次还能否找到

---

## 问题只分三类

### P0

包括：

- 数据丢失
- 数据安全
- 权限泄露
- 登录不可用
- 系统无法使用

结论：

> 阻塞上线。

### P1

包括：

- 首个核心工作闭环无法完成
- 核心入口找不到
- 必须依赖管理员手工修数据才能继续

结论：

> 阻塞上线。

### P2

包括：

- 视觉
- 文案
- 体验
- 路径不够顺
- 新需求
- 长期优化
- 扩展功能

结论：

> 不阻塞上线，进入上线后迭代池。

---

## Gate 4 通过条件

- 一名真实老师可以独立完成核心工作
- P0 清零
- 影响核心闭环的 P1 清零
- P2 被记录，但不继续阻塞

达到这里：

> 可以立即向第一批公司老师开放正式账号。

不需要再额外等待。

---

# 十四、完整上线状态

最终应该形成一个非常简单的状态表。

```text
Gate 0  上线范围冻结            PASS / BLOCKED / UNKNOWN
Gate 1  正式身份与数据成立      PASS / BLOCKED / UNKNOWN
Gate 2  真实工作闭环跑通        PASS / BLOCKED / UNKNOWN
Gate 3  最小生产保障成立        PASS / BLOCKED / UNKNOWN
Gate 4  真实老师独立验收        PASS / BLOCKED / UNKNOWN
```

当全部为 `PASS`：

# 立即上线

这里的上线定义为：

> Mathin 正式进入公司内部生产使用。

不是等待 Production 1.0。

不是等待整个 R1 清空。

---

# 十五、R1 原有工作如何重新定位

原有 R1 不需要推翻。

只需要重新分类。

| 原 R1 类型 | 在 R1-Live 中的处理 |
|---|---|
| 账号、权限 | 与 Gate 1 / Gate 2 有关的部分立即做 |
| 组织隔离 | Gate 1 必须 |
| 核心流程 Bug | Gate 2 必须 |
| 日志、备份、回退 | Gate 3 做最小版本 |
| 全量内容盘点 | 上线后 |
| 全量课件导入 | 上线后 |
| 所有页面完整性 | 只修核心闭环涉及页面 |
| 完整视觉收口 | 不阻塞，除非影响操作 |
| 全量 Playwright | 上线后逐步扩大 |
| 全量指标 | 上线后 |
| 完整审计证据 | 上线后 |
| 14 天 RC | 改为真实老师上线后的运行观察 |
| 3D / Spatial Math | 独立并行 |
| 财务深度建设 | 后续业务项目 |
| 活动系统继续扩展 | 后续业务项目 |

---

# 十六、为什么“14 天 RC”应放到真实使用以后

之前如果设计为：

```text
没有真实用户
→ RC 14 天
→ 再正式上线
```

其实价值有限。

因为：

- 没有真实操作
- 没有真实错误
- 没有真实交互路径
- 很多问题不会出现

更合理的是：

```text
小范围正式上线
→ 第一批老师真实使用
→ 观察 14 天
→ 根据真实问题继续 Harden
→ 再扩大范围
```

因此：

> 内部真实使用本身就是最有价值的 RC。

# 十七、3D / Spatial Math 的独立施工规则

3D 继续作为并行轨道。

推荐规则：

1. 使用独立路由
2. 使用独立权限或 feature flag
3. 默认普通教师不可见未完成能力
4. 3D 迁移不得破坏主业务数据库
5. 3D 不进入 R1-Live Gate
6. 修改共享依赖时必须验证主系统构建
7. 修改认证、权限、导航、课堂主链路时必须回归 R1-Live Smoke Test
8. 3D 可以持续施工，不需要等待 R1-Live
9. R1-Live 也不需要等待 3D

推荐思路：

```text
主轨：R1-Live
支轨：Spatial / 3D
```

二者可以并行，但不能互相绑死。

# 十八、用户本人接下来真正应该做什么

讨论最后明确了一点：

代码审阅、修复、测试、部署、检查，都可以大量交给 Agent。

用户本人真正无法外包的事情包括：

---

## 1. 决定首个真实教师工作闭环

这是目前唯一仍需要产品负责人明确的核心事项。

```text

→ 打开真实课次与课程内容
→ 保存一次课堂结果 / 学习结果 / 课后跟进
```

如果当前仓库中某一项记录方式明显更加成熟，Agent 可以选择最小修改量的那一个。

## 2. 决定哪些缺陷可以接受

Agent 可以发现问题。

但只有产品负责人可以决定：

> 这个问题是否值得阻止老师开始使用。

默认规则：

- P0 阻塞
- 核心 P1 阻塞
- P2 不阻塞

## 3. 选择第一位真实老师

找一名：

- 熟悉业务
- 愿意反馈
- 可以直接交流

的老师。

让他真正使用。

---

## 4. 观察，而不是指导

真实用户第一次操作产生的信息非常重要。

产品负责人应重点判断：

- 实际工作和系统结构是否匹配
- 导航是否符合真实老师心智
- 哪些设计问题是工程审查无法发现的
- 哪些所谓“需要优化”其实老师根本不在乎
- 哪些看起来不起眼的问题反而会真正阻止使用

# 二十、Agent 后续施工方式必须改变

过去容易形成：

```text

→ 自动施工 R1-9
→ 完成 R1-9
→ 自动施工 R1-10
→ ...
```

新的施工逻辑必须改成：

```text

→ 找出让 Gate BLOCKED 的最小问题集
→ 只修这些问题
→ 重新验收

→ 进入下一 Gate
```

- 可以更漂亮
- 可以做更多动画
- 可以支持更多内容
- 可以增加更多导入格式
- 可以再完善一层权限抽象
- 可以再增加一套审计
- 可以再新增一个后台页面
- 可以扩展更多 3D 能力
- 可以顺手统一所有历史组件

这些可以记录为后续项。

但：

> 不进入当前 Gate 的施工。

# 二十一、Agent 的第一项具体任务

Agent 不应马上继续改代码。

首先应基于当前最新仓库输出一张：

# R1-Live 上线差距表

格式固定如下：

| Gate | 当前状态 | 已完成证据 | 缺失项 | 是否阻塞 | 最小修复范围 |
|---|---|---|---|---|---|
| Gate 0 | PASS / BLOCKED / UNKNOWN / NOT REQUIRED | | | | |
| Gate 1 | PASS / BLOCKED / UNKNOWN / NOT REQUIRED | | | | |
| Gate 2 | PASS / BLOCKED / UNKNOWN / NOT REQUIRED | | | | |
| Gate 3 | PASS / BLOCKED / UNKNOWN / NOT REQUIRED | | | | |
| Gate 4 | PASS / BLOCKED / UNKNOWN / NOT REQUIRED | | | | |

---

## 状态只允许四种

```text
PASS
BLOCKED
UNKNOWN
NOT REQUIRED
```

不得增加模糊状态。

---

## 对每一个 BLOCKED

必须给出：

- 具体阻塞原因
- 对应代码 / 数据 / 配置位置
- 最小修复方案
- 是否需要用户人工操作
- 验收方法

---

## 对每一个 UNKNOWN

必须说明：

- 为什么不能从代码判断
- 需要怎样的真实运行验证
- 谁执行验证
- 验证结果如何改变 Gate 状态

# 二十二、建议的首个真实闭环

如果用户没有进一步调整，Agent 可以默认采用以下闭环作为分析基准：

```text
正式教师登录
→ 进入正确组织
→ 看到自己的课表 / 班级
→ 打开真实课次
→ 打开或查看对应课程内容
→ 完成一次课堂结果 / 学习结果 / 课后跟进记录

→ 退出并重新登录

→ 管理员在正确权限范围内可见
→ 无权限用户不可见
```

## 首个闭环选择原则

如果系统中：

- 学习结果已经最成熟
- 课后跟进比学习结果成熟
- 出勤记录最成熟

Agent 应选择：

> 修改量最小、真实业务价值足够、最能证明“老师已经开始使用 Mathin”的那个闭环。

不要求一次验证所有业务子模块。

# 二十三、对之前工程建议的处理

第一次代码审阅中提出的工程问题仍然保留。

但现在需要重新按 R1-Live 判断优先级。

如果会让真实老师无法判断保存 / 读取故障：

## 全量 Playwright 不足

不要求马上覆盖整个系统。

> 不应该因为“大文件”阻塞上线。

如果首个闭环依赖：

> 只修会影响稳定性的部分，不进行全量重构。

## Terms 内容深度不足

明确：

> 不阻塞 R1-Live。

## 3D 模块继续施工

明确：

> 并行，不阻塞。

# 二十五、最核心的决策

当前 Mathin 不是缺少更多待办。

真正缺少的是：

> 一个“会明确结束”的上线项目。

这个项目就是：

# R1-Live

它的目标不是证明 Mathin 已经完美。

它只证明一件事：

> **Mathin 已经可以开始被真实老师用于真实工作。**

从此以后：

- 内容可以在真实系统上逐步增加
- UI 可以根据真实反馈继续优化
- 3D 可以继续并行开发
- 财务和活动可以按真实业务需求继续完善
- R1 剩余工程可以根据真实生产问题重新排序
- Production 1.0 可以在有真实使用数据以后再定义

# 二十八、讨论最终结论

当前最重要的方向不是：

> “Mathin 还可以继续做什么？”

而是：

> “Mathin 还缺哪几个不可绕过的条件，才能让第一名真实老师正式开始使用？”

这两个问题看起来很接近，但会产生完全不同的施工方式。

前者会无限产生待办。

后者会产生一个有限的 Gate 列表，并最终清零。

因此，后续所有 Agent 的分析和施工都应围绕：

# **让 R1-Live 的 Gate 清零，而不是继续扩大 R1。**
