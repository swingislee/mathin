# Base 全字段业务资料整理

本轮以已经归档的 Base 原文为输入，逐个字段保存业务语义、规范值、原文、来源字段 ID 和映射版本。学生与家庭、获客、沟通、确认、到访、测评、报名、服务人员、续报、缴费、教学、竞赛、内容、资源及运营目标分别整理；每条来源记录保留自己的值。

当前主来源的 20 张表有 345 个字段定义，其中 274 个字段曾填写内容。空白模板字段也登记去向，新增未知字段继续保存，并在报告中单列。较早 Base 快照作为独立来源处理，不与最新来源覆盖合并。

## 页面中的使用

- 线索表读取 Base 获客来源，补齐来源地点、获取日期、渠道和获取人员。展开线索后可查看各次获客的触达内容和原组别；列筛选支持触达内容、获客组别和原获取日期。原有小地推来源仍保留其主行，各次 Base 来源单独列出。
- 学生 360 中的“查看原表资料与相关记录”先按业务内容分组展示，随后可以展开原字段核对。不同来源的状态、人员与同名字段分别保存，可能重复提示沿用已有规则。
- 管理员的历史导入页可查看全部已归档表，包括内容产出、目标拆解、日报、学习记录和资源表；详情增加整理后的业务资料，原字段继续保留。

## 字段合同

`history_source_business_facts` 以 `(source_record_id, mapping_version)` 唯一标识一份资料。`fields` 数组的每个元素保存来源字段 ID、原字段名、业务分组、语义键、类型、规范值、显示值、原文、原类型和转换状态。相同语义键允许来自不同字段，数组保留各字段自己的值。

第三版在第二版同义值规则上增加错填归位、同格多类资料拆分、子女资料和“资料待补”状态。读取每条记录最新的受支持版本，第一、二版继续保留。来源资料展示规范值、存在差异时的原文，以及仍需核对的原因。线索表在列筛选和分页前统一单一年级的文字与数字写法；现有整数年级有值时沿用该值。该读取适配不回写身份、当前年级或已保存的跟进结论。

| 来源表达 | 整理结果 |
| --- | --- |
| 完整年月日、紧凑日期 | 校验真实日历后保存日期；保留原写法 |
| 月日、月份、年份 | 保存对应精度，年份缺失时保持缺失 |
| 带时区的本地日期时间 | 保存原时区和时间精度 |
| “第 1 天”等缴费时间 | 保存相对天数和空的基准日期 |
| 手机号及多个联系号码 | 规范国家码和分隔符，各号码分别保存；团成员电话仍属于获客资料 |
| 年级及旧学年的年级 | 保存可识别整数和来源所指年份；明确升年级表达按目标年级整理 |
| 测评分数、等级、成绩下限 | 分别保存；原“未达 A”沿既有规则对应 X+ |
| “慎思”等历史班型名称 | 保存班型原文；本轮确认的“慎思—”对应 A |
| 新报、不续报、已退费 | 保留不同结果，不把新报当作续报成功 |
| 金额 | 保存十进制金额与来源币种，不生成新的收款事实 |
| 人员、组别、校区 | 保存来源署名与标签，身份和权限仍沿用现有关系 |
| 文字、选项、链接、附件引用 | 保存业务类别与原值；附件本体仍沿原档案能力访问 |
| 错填或同格多类资料 | 按业务含义归位；学校与年级分别展示，同一原字段仍可追溯 |
| 明确未知、无效号码或已无显示名称的原选项 | 导入并标记“资料待补”，保留原文、原选项值与来源引用 |

### 当前规范化规则（第三版）

- 年级字段兼容中文数字、阿拉伯数字、全角字符、学段简称、完整学段名称及重复“年级”后缀。来源历史资料保存 1–12 年级；小学、初中、高中按对应学段解释。幼儿园阶段单独保存，适用学年继续由来源字段表达。按产品负责人本轮确认，“三奶奶及”对应 3 年级、“一升年级”与“二？年级”对应 2 年级、“五六年级”对应 6 年级；“二升三”等明确升年级表达使用目标年级。
- 组别、班序、月份和周次使用一致的数字及单位；星期几、年度第几周和某月第几周保存不同单位，校区和人员关系继续保持各自来源。
- 到访、报名、加微信、诺访、领取、开团、填写、旁听等使用各字段自己的肯定／否定规则及完整标签。相同的“是”在不同字段中仍属于各自业务含义。续报、新报、未续报与已退费分别保存；寒假、春季的混合结果逐季表达。
- 产品负责人于 2026-09-10 明确确认：意向分类与体系兴趣度统一为 A＝高、B＝中、C＝低。规范显示使用 A/B/C，原“高／中／低”仍可核对。测评的 A 与 A+、不同测评尺度和历史班型继续分别保存。
- 时段统一全角／半角冒号、分号、点号及“点／半”的明确表达；按产品负责人确认，没有注明上下午的 1–7 点按下午转换为 24 小时制。明确写出的上午、凌晨与“后”等时间关系继续保留。“12.10'”等尾部误写按 12-10 整理。
- 获客渠道按完整、含义明确的写法归一，例如家长介绍／家长推荐；有具体人员、来源项目或校区的内容保留其区别。校名只统一相同编号、同一校区标记或同一道路名称；其他学校简称保持原文。
- 多选项去重并按稳定顺序展示，顺序变化不产生不同的规范值；加微信字段同时出现“未加V与群”和“已加V”时按已加 V 整理，入群事实仍以来源为准。“暂无结果、加V”分别表达已加 V 与待下次沟通。其他确实冲突的状态保留核对提示。金额按十进制精确转换人民币、千元和万元表达，财务来源资料继续独立于实际收款事实。
- 广场、商场及“附近”地点进入“附近地点”，门口、停车点与地推地点进入“获取地址”；线索表汇集同一次来源内各字段的获取地址。金字塔老生进入获客来源，秋季限定继续保存；公开课、数独与思维闯关等进入“意向内容”，具体跟进描述进入备注。历史职员署名单独保存；无法判断的“小宝”移入其他资料。
- 学校和年级写在一个单元格时分别投影到对应业务分组，原字段 ID、字段名和原文保留一份。明确缺失、不可用号码、失去显示名称的旧选项保存为“资料待补”，允许继续导入和浏览；仍需判断业务归属的内容进入待确认清单。

### 同一家庭的多个孩子

明确写有两个孩子的年级时，建立稳定的家庭来源键和独立子女键，分别保存年级、称呼状态及明确写出的姐姐、妹妹等关系，共用原家庭联系方式。单个原线索称呼作为家庭来源标签保留。姓名有独立来源支持时，可结合已经关联的同一线索、相同电话、同名与唯一对应年级补入，并保存来源 ID 与摘要；其余子女姓名标为“资料待补”。

这份结构保存来源子女资料，正式学生和家庭关系通过现有业务流程办理。

### 多名学员的活动安排

产品负责人于 2026-09-11 确认，多人安排先保存最可能的档案匹配，并在档案中沿用待核对标签。逐行解析姓名、目标年级、活动、星期与时段，结合各人的同名资料、到访日期、时段和学服老师排序；每个候选取一条个人来源的最佳证据，重复快照不累加分数。同名候选与匹配依据继续保留，无候选时保留原资料。

`history_source_fragments` 保存每个孩子对应的原始行、来源字段、行号、摘要和推定目标，支持现有学生或线索。360 的“查看原表资料与相关记录”合并读取当前对象的片段，并沿用现有 `Badge` 和“资料关联待核对”文案；原整条来源及 Base 第一至三版继续保留。线索后续确认到学生时，其来源片段随现有关联进入学生档案。该操作保存来源安排，当前业务阶段与活动办理继续使用原领域流程。

本机执行入口为 `scripts/base-activity-source-links.mjs --prepare SOURCE_ID`，随后依次使用 `--check`、`--apply`、`--verify`；同样执行本机目标核对、输入指纹、回滚权限检查、既有数据指纹与逐项再读。私有匹配清单位于 gitignored `.tmp/base-activity-associations/`。

本轮补充的是可读取、可追溯的结构化来源业务资料。领域主表继续管理当前身份、人员关系、工作阶段、报名、班级、考勤和账务；整理不通过覆盖这些事实来“填满”字段。

## 执行和校验

字段语义入口是 `scripts/lib/base-business-fields.mjs`，同义值规则位于 `scripts/lib/base-value-normalization.mjs`，错填归位和家庭子女整理分别位于 `scripts/lib/base-field-placement.mjs`、`scripts/lib/base-family-organization.mjs`，通用年级解析复用 `src/lib/grade-format.mjs`。`buildBaseBusinessPlan` 按来源表和字段 ID 输出完整报告，区分规范值、文字和资料待补；`auditBaseBusinessValues` 对照上一版，按 JSON 内容而非对象键顺序计算差异，并列出每组实际同义值、归位结果与待核对的原值。

以下命令只用于已核对的本机隔离开发目标：

```powershell
node --experimental-strip-types scripts/base-business-fields.mjs --preflight
node --experimental-strip-types scripts/base-business-fields.mjs --prepare
node --experimental-strip-types scripts/base-business-fields.mjs --check
node --experimental-strip-types scripts/base-business-fields.mjs --apply
node --experimental-strip-types scripts/base-business-fields.mjs --verify
```

执行器核对主机、实际 Supabase origin、监听进程、Docker 网络和数据库标识。清单及检查结果包含代码、映射、SQL、来源输入和子女独立来源凭据的指纹。应用前验证当前清单；写入逐条核对原文和来源摘要，同一映射版本的不同结果会被拒绝。原业务表与旧映射版本的计数、指纹在事务内前后核对。检查事务会回滚，并核对三个受影响 RPC 的定义和权限恢复；版本选择覆盖第一、二版回退、第三版优先及未来未支持版本隔离。

原表全量导入与运营导入也接入同一保存函数，后续重新导入时一并保存字段资料。执行原表全量导入使用 `node --experimental-strip-types scripts/full-source-import.mjs`。本轮资料补齐使用上述专用执行器，不重跑旧运营导入。

第三版的 `plan.json`、逐字段报告、`value-audit.json`、执行指纹及错误明细保存在 gitignored `.tmp/base-data-organization/v3/`。`review-values.md` 分列待确认、子女资料和资料待补，`resolved-values.md` 记录本轮逐项处理结果。第二版证据保留在 `v2/`，第一版保留在父目录。清单和待核对记录含个人资料，按现有受控开发资料管理。共享证据只记录字段名、汇总和不含个人资料的同义表达。
